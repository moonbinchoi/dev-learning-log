# 캐시 무효화 규칙은 말로 맞히고 예측에는 못 썼다: 방향(아래로만)과 부모 레이어 조건

4회차(2026-10-14). docker-lab 앱 생성 → Dockerfile 작성 → 빌드·history → 캐시 실험(C-9·C-10) → 컨텍스트·`.dockerignore` → labnet에서 실행을 예측 후 실행했다.

- C-9: `RUN sleep 15`를 COPY 뒤에 두고 jar를 바꾼 빌드에서, 근거로 "COPY 뒤는 모두 깨진다"고 말하면서 "15초보다 적게"를 예측했다. 실제 15.2초. 명령 문자열이 같아도 아래 레이어가 다르면 캐시가 안 맞는다는 것을 여기서 처음 봤다.
- C-10: RUN을 COPY 위로 옮긴 뒤 jar만 바꾼 빌드에서 "RUN부터 다시"를 예측했다. 실제 RUN CACHED, COPY부터(2.3초 vs C-9의 17.9초). 무효화가 바뀐 단계에서 아래로만 번진다는 방향을 예측에 쓰지 못했다.
- B-6·B-8: 단계 수와 history 줄 수를 둘 다 "Dockerfile 줄 수(5)"로 예측했다. 실제 Dockerfile 단계는 `[1/3]`~`[3/3]`(EXPOSE·ENTRYPOINT는 설정만), history는 베이스 이미지 기록을 포함해 20줄. WORKDIR가 8.19kB(폴더 생성)인 것도 확인했다.
- D-11: 컨텍스트 22.60MB를 "폴더 전체"로 예측했다. jar 크기(22,590,800B)와 같아 빌더가 필요한 파일만 가져간다는 것을 숫자로 확인했다. 119B는 jar가 직전 빌드와 같을 때 나왔다(메커니즘은 문서에서 못 찾음).
- B-5: COPY 원본을 Maven `target/`, 이어서 Windows 절대 경로로 썼다. 빌더는 VM 안에 있고 컨텍스트 상대 경로만 본다는 설명 뒤 고쳤다.
- E-14: 컨테이너 안 `localhost` = 자기 자신을 맞혔다(`Connection refused`). 브라우저가 3회차 nginx 페이지를 캐시해 보여 준 것을 결과로 믿었고, E-15에서도 "nginx"를 예측했다가 근거를 묻자 고쳤다.

맞힌 것: 재빌드 시 CACHED·0.8초, COPY 크기 = jar(힌트 후), `.dockerignore`에 `build`를 넣으면 COPY not found, 재빌드 전송량 22.6MB, `v3 hello`. `.dockerignore`에 jar 이름을 박으면 버전마다 고쳐야 한다는 문제를 스스로 짚었다(→ `!build/libs/*.jar`, COPY 와일드카드는 jar가 둘이라 불가).

면접: Q1(순서와 캐시)은 "어긋난 시점부터 뒤가 모두 깨진다"는 핵심만, 순서 원칙(느리고 안 바뀌는 것 위)과 숫자(17.9초 vs 2.3초) 빠짐, "무결성"이라는 부정확한 말을 씀. Q2(DB 주소)는 환경 변수 맞음, `-e SPRING_DATASOURCE_URL`·E-14/E-15가 같은 이미지라는 근거 빠짐, 고정 시 결과를 "Dockerfile 수정"이라 함(정답: 환경마다 이미지를 다시 빌드 → 검증한 이미지와 배포 이미지가 달라짐, 비밀번호가 이미지 설정에 남음). Q3(2회차 Q3 다섯 번째)는 VM 경계와 변경 이벤트 둘 다 답했다. "inotify"라는 단어는 쓰지 않았다.

## Implications
- 5회차 회상 퀴즈: C-10 상황(RUN이 COPY 위, jar만 바뀜)에서 다시 실행되는 단계와 그 이유, 컨테이너 안 `localhost`가 DB에 닿지 않는 이유.
- 5회차 compose의 `environment:`가 오늘의 `-e SPRING_DATASOURCE_URL`이다. Q2의 "같은 이미지, 다른 설정"을 여기서 다시 묻는다.
- 5회차 시작 전 Dockerfile의 `RUN sleep 15` 줄을 사용자가 지운다(실험용).
- 면접 답은 계속 숫자·명령을 빠뜨린다. "오늘 본 숫자 하나"를 답에 넣도록 요구한다.
