4회차 · 이미지 만들기

오늘의 성과: 직접 쓴 Dockerfile로 docker-lab:1 이미지를 만들고, labnet에 띄워 브라우저에서 2회차의 hello를 본다.

지금까지는 남이 만든 이미지(nginx, postgres)만 썼다. 오늘은 내 앱을 이미지로 만든다. 5회차 Compose의 build: .는 오늘 쓰는 Dockerfile을 그대로 읽는다. 7회차 shop dev container도 같은 원리로 이미지를 만든다. 용어는 용어집을 따른다.

1. Dockerfile → 이미지

  • 레이어는 파일 추가·삭제·수정의 묶음이다. 한번 만들면 바뀌지 않고, 여러 이미지가 같은 레이어를 함께 쓴다. (Understanding image layers)
  • 1회차의 쓰기 가능한 컨테이너 레이어는 create가 이 레이어 더미 맨 위에 더하는 한 장이다.

2. 오늘 쓰는 Dockerfile 명령

명령하는 일
FROM 이미지베이스 이미지. Dockerfile은 FROM으로 시작해야 한다. (FROM)
WORKDIR 경로뒤에 오는 RUN·COPY·ENTRYPOINT 등의 작업 디렉터리. 기본값은 /. (WORKDIR)
COPY 원본 대상빌드 컨텍스트(4절)의 파일을 이미지 안으로 복사한다. (COPY)
RUN 명령빌드할 때 명령을 실행하고 결과를 새 레이어로 남긴다. (RUN)
ENV 키=값환경 변수. 만든 이미지에 남아 컨테이너에서도 보인다. (ENV)
EXPOSE 포트3회차에서 본 문서용 표시. publish하지 않는다. (EXPOSE)
ENTRYPOINT [..]컨테이너가 시작할 때 실행할 명령. 빌드 때는 실행하지 않는다. (ENTRYPOINT)
CMD [..]기본 명령이나 ENTRYPOINT의 기본 인자. docker run 이미지 명령의 뒤쪽 명령이 이것을 덮어쓴다. 둘의 조합은 이 표에 있다.

exec form과 shell form. ENTRYPOINT ["java", "-jar", "app.jar"]처럼 JSON 배열로 쓰면 exec form이다. 명령이 셸 없이 바로 실행된다. ENTRYPOINT java -jar app.jar처럼 쓰면 shell form이고, /bin/sh -c를 거쳐 실행된다. exec form은 큰따옴표를 써야 한다. (Shell and exec form)

1회차와 연결. 컨테이너의 수명은 주 프로세스에 묶인다. exec form이면 java가 바로 그 주 프로세스가 된다. shell form이면 주 프로세스는 sh다. 그러면 docker stop의 SIGTERM이 java에 닿지 않을 수 있다. (ENTRYPOINT)

3. 빌드 캐시 — 오늘의 핵심

Docker는 명령마다 이전 빌드에서 만든 레이어를 재사용할 수 있는지 본다.

  • 명령과 정확히 일치하는 캐시 레이어가 없으면 그 단계의 캐시가 무효가 된다. (Cache invalidation)
  • 한 단계가 무효가 되면 그 뒤의 모든 단계가 다시 실행된다. (Docker build cache)
  • COPY는 복사할 파일 내용의 체크섬으로 비교한다. 파일 수정 시각은 보지 않는다. (Cache invalidation)
  • RUN은 명령 문자열만 비교한다. 같은 apt-get update는 패키지가 새로 나와도 캐시를 쓴다. (Cache invalidation)
  • 그래서 잘 안 바뀌는 단계를 위에, 자주 바뀌는 단계를 아래에 둔다. (Optimize cache usage)

4. 빌드 컨텍스트와 .dockerignore

  • docker build .의 .이 빌드 컨텍스트다. 빌드가 접근할 수 있는 파일 전체이며, COPY는 이 안의 파일만 가져올 수 있다. (Build context)
  • 2회차 구조대로 docker CLI는 Windows에, 빌더는 WSL 2 VM 안에 있다. 빌더는 필요한 파일을 필요할 때 컨텍스트에서 가져간다. (Local context)
  • 컨텍스트 루트의 .dockerignore에 적은 경로는 컨텍스트에서 빠진다. 빌더가 가져갈 수도, COPY할 수도 없다. !로 시작하는 줄은 예외(다시 포함)다. (.dockerignore files)

5. 오늘 쓰는 명령

명령하는 일
curl.exe … -o app.zipSpring Initializr에서 프로젝트 zip을 받는다. -d 키=값이 프로젝트 옵션이다. PowerShell의 curl은 다른 명령의 별칭이라 curl.exe로 쓴다.
tar -xf app.zipzip을 현재 폴더에 푼다. Windows 11에 들어 있다.
.\gradlew.bat bootJar호스트 JDK로 실행 가능한 jar를 build/libs/에 만든다.
docker build -t 이름:태그 .현재 폴더를 컨텍스트로, 그 안의 Dockerfile로 이미지를 만들고 이름을 붙인다. (build -t)
--progress=plain빌드 진행을 접지 않고 단계별 줄로 모두 출력한다. (build --progress)
docker history 이미지이미지의 레이어를 위(최신)부터 보여 준다. 줄마다 만든 명령과 크기가 나온다. (docker history)
run -e 키=값컨테이너에 환경 변수를 넣는다. 3회차 PGPASSWORD와 같다. (run -e)
SPRING_DATASOURCE_URLSpring Boot는 spring.datasource.url을 이 이름의 환경 변수로도 읽는다. 점은 _로, 전부 대문자로 바꾼 이름이다. 환경 변수가 application.properties보다 우선한다. (Spring Boot — Binding from environment variables)

6. 실습 — 예측하고 직접 친다

PowerShell(lab 터미널)에서 projects/docker-lab으로 이동해 친다. 명령마다 예측을 먼저 말하고, Clear-Host 후 실행한 뒤 @terminal:lab으로 보여 준다.

A. 앱 준비 (예측 없음)

  1. Initializr에서 Spring Boot 4.1.1, Java 25, Gradle 프로젝트를 받아 푼다. 의존성은 Web·JDBC·PostgreSQL Driver다.

    cd E:\Study\Inflearn\projects\docker-lab
curl.exe https://start.spring.io/starter.zip -d type=gradle-project -d bootVersion=4.1.1 -d javaVersion=25 -d groupId=com.study -d artifactId=docker-lab -d name=docker-lab -d packageName=com.study.dockerlab -d dependencies=web,jdbc,postgresql -o app.zip
tar -xf app.zip
Remove-Item app.zip

  2. src/main/java/com/study/dockerlab/MemoController.java를 만든다. /로 요청하면 2회차에 넣은 memo 테이블의 첫 줄을 돌려준다. Spring 설명은 이 트랙에서 다루지 않는다.

    package com.study.dockerlab;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
class MemoController {

    private final JdbcTemplate jdbc;

    MemoController(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @GetMapping("/")
    String memo() {
        return jdbc.queryForObject("SELECT t FROM memo LIMIT 1", String.class);
    }
}

  3. src/main/resources/application.properties에 DB 접속 정보를 더한다. 주소는 일부러 localhost로 둔다(E-8에서 쓴다).

    spring.datasource.url=jdbc:postgresql://localhost:5432/docker_lab
spring.datasource.username=postgres
spring.datasource.password=pw

  4. 호스트에서 jar를 만든다.

    .\gradlew.bat bootJar
Get-ChildItem build\libs

B. Dockerfile 쓰고 빌드하기

  1. projects/docker-lab/Dockerfile을 직접 쓴다. 2절의 표를 보고 아래를 만족시킨다. 다 쓰면 Claude에게 리뷰를 받는다.

    • 베이스 이미지는 eclipse-temurin:25-jre다. JDK가 아니라 실행에 필요한 JRE만 든 이미지다. (eclipse-temurin)

    • 4번에서 만든 jar를 app.jar라는 이름으로 복사한다.
    • 앱이 8080을 쓴다는 것을 적어 둔다.
    • 컨테이너가 시작하면 java -jar app.jar를 exec form으로 실행한다.

  2. 첫 빌드.

    docker build --progress=plain -t docker-lab:1 .
    #으로 시작하는 단계 번호는 몇 번까지 나올까? Dockerfile 줄 수와 같을까? eclipse-temurin은 아직 내려받은 적이 없다. 출력의 어디에서 그것이 드러날까?

  3. 아무것도 바꾸지 않고 똑같이 다시 빌드한다.

    걸리는 시간은 6번과 비교해 어떨까? 단계마다 어떤 표시가 붙을까? docker images의 docker-lab 줄은 몇 개일까?

  4. 레이어를 본다.

C. 캐시가 깨지는 지점

  1. 시간이 오래 걸리는 의존성 설치를 흉내 낸다. Dockerfile의 COPY 바로 아래에 한 줄을 넣는다. sleep 15는 15초를 기다린다.

    RUN sleep 15 && echo ready > /ready.txt

    빌드를 한 번 해서 캐시를 채운다.

    docker build --progress=plain -t docker-lab:1 .

    그다음 MemoController의 반환값을 "v2 " + jdbc.queryForObject(...)로 바꾸고 jar와 이미지를 다시 만든다.

    .\gradlew.bat bootJar
docker build --progress=plain -t docker-lab:1 .
    어느 단계부터 다시 실행될까? 15초를 다시 기다릴까? 근거를 3절에서 찾는다.

  2. RUN sleep … 줄을 COPY 위로 옮기고 한 번 빌드한다. 반환값을 "v3 "로 바꾸고 다시 만든다.

    docker build --progress=plain -t docker-lab:1 .
.\gradlew.bat bootJar
docker build --progress=plain -t docker-lab:1 .
    전송 크기는 어떻게 바뀔까? 이번 빌드에서 COPY 단계는 캐시를 쓸까?

D. 빌드 컨텍스트

  1. B-6 출력의 #4 load build context 아래 transferring context: 22.60MB가 있었다. build/libs의 jar는 22,590,800바이트다.

    이 폴더에는 jar 말고도 .git, .gradle, src/, build/의 다른 파일이 있다. 22.60MB에는 무엇이 들어 있었을까? B-7에서는 같은 줄이 119B였다. 왜일까?

  2. projects/docker-lab/.dockerignore를 만들고 한 줄만 적는다. build 폴더를 컨텍스트에서 뺀다는 뜻이다.

    build
    docker build --progress=plain -t docker-lab:1 .
    빌드는 성공할까? 실패한다면 어느 단계에서, 어떤 메시지로 실패할까?

    확인한 뒤 .dockerignore를 직접 고친다. jar는 남기고 나머지(.git, .gradle, src, bin)는 빼는 것이 목표다. 4절의 ! 예외를 써도 된다. 리뷰를 받고 다시 빌드한다.

문서가 드는 .dockerignore의 목적은 필요 없는 파일을 빌더로 보내지 않아 빌드를 빠르게 하는 것이다. 원격 빌더일 때 특히 그렇다. (.dockerignore files) 또 컨텍스트에서 빠진 파일은 COPY할 수 없으므로, COPY . .처럼 폴더를 통째로 복사해도 이미지에 들어가지 않는다.

E. 내 이미지를 labnet에 띄운다

  1. 3회차처럼 postgres를 labnet에 띄운다. 이번에는 처음부터 --network로 붙인다.

    docker run -d --name pg --network labnet -e POSTGRES_PASSWORD=pw -v pgdata:/var/lib/postgresql postgres:18

  2. 앱 컨테이너를 같은 네트워크에 띄우고 호스트 8081을 앱의 8080에 publish한다. 환경 변수는 아직 주지 않는다.

    docker run -d --name app --network labnet -p 8081:8080 docker-lab:1
docker logs app
    앱은 뜰까? 통합 브라우저로 http://localhost:8081을 열면 무엇이 보일까? 이 컨테이너 안에서 localhost:5432는 무엇을 가리킬까?

  3. 환경 변수로 DB 주소를 바꿔 다시 띄운다. 이미지는 다시 빌드하지 않는다.

    docker rm -f app
docker run -d --name app --network labnet -p 8081:8080 -e SPRING_DATASOURCE_URL=jdbc:postgresql://pg:5432/docker_lab docker-lab:1
    http://localhost:8081에 무엇이 나올까? pg라는 이름은 누가 IP로 바꿔 줄까?

7. 남겨 둘 것

5회차에 오늘의 docker run 두 줄을 compose.yaml로 옮긴다. Dockerfile, .dockerignore, 앱 코드, labnet, pgdata는 남긴다. 컨테이너 app과 pg는 지워도 된다.

더 읽을 것

1차 자료: Docker docs — Docker build cache. 캐시가 무효가 되면 뒤 단계가 모두 다시 실행되는 그림이 있다. 이어서 Cache invalidation에서 명령별 비교 규칙을 읽는다.

실무에서는 jar 하나를 통째로 COPY하면 의존성 라이브러리와 내 코드가 한 레이어에 들어간다. Spring Boot는 jar를 여러 레이어로 나누는 방법을 제공한다. 이 트랙에서는 다루지 않는다. (Spring Boot — Efficient container images)
