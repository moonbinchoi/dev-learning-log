2회차 · 데이터

오늘의 성과: postgres 컨테이너를 지웠다가 다시 만들어도 테이블이 남아 있게 한다. 데이터가 어디에 사는지 말할 수 있다.

1회차에서 start 뒤에는 mark.txt가 남아 있었다. 같은 컨테이너의 쓰기 가능한 컨테이너 레이어에 있었기 때문이다. 그런데 DB는 이미지를 바꾸면 컨테이너를 새로 만든다. 5회차 Compose와 7회차 shop dev container도 컨테이너를 수시로 지우고 다시 만든다. 그때도 데이터가 남으려면 레이어 밖에 저장해야 한다. 용어는 용어집을 따른다.

1. 데이터는 세 곳에 산다

  • 쓰기 레이어는 컨테이너마다 따로 있다. 컨테이너를 지우면 함께 사라지고, 다른 컨테이너에서 꺼내 쓰기 어렵다. (Storage overview)
  • 볼륨(volume)은 Docker 데몬이 만들고 관리하는 저장소다. 컨테이너를 지워도 남는다. 호스트에서 볼륨 데이터에 직접 접근하는 것은 지원하지 않는다. (Volumes)
  • bind mount는 호스트의 경로를 컨테이너에 그대로 연결한다. 호스트와 컨테이너가 둘 다 파일을 고칠 수 있고, Docker가 둘을 격리하지 않는다. (Bind mounts)

근거: Volumes(복사, volume-nocopy), Bind mounts(가려짐, 경로 자동 생성), WSL best practices(속도).

이름 없는 볼륨도 있다. 볼륨 이름을 생략하면 Docker가 무작위 이름을 붙인다(anonymous volume). 이미지의 Dockerfile에 VOLUME이 선언돼 있으면 -v를 안 줘도 그 경로에 anonymous volume이 붙는다. docker rm -v는 anonymous volume만 지우고 named volume은 남긴다. (docker rm -v)

postgres 이미지에서 알아 둘 것

  • POSTGRES_PASSWORD만 필수다. POSTGRES_DB를 안 주면 사용자 이름(postgres)이 DB 이름이 된다.
  • 18 이상은 VOLUME이 /var/lib/postgresql이고, 실제 데이터는 그 아래 18/docker에 있다. 17 이하는 /var/lib/postgresql/data다. 그래서 오늘은 postgres:18로 버전을 고정한다.
  • POSTGRES_* 변수는 데이터 디렉터리가 비어 있을 때만 효과가 있다. 이미 DB가 있으면 건드리지 않는다.

근거: postgres 공식 이미지의 Environment Variables, PGDATA 절.

4. 실습 — 예측하고 직접 친다

PowerShell에서 projects\docker-lab으로 이동해서 친다. 명령마다 예측을 먼저 말하고, Clear-Host 후 실행한 뒤 @terminal로 보여 준다.

cd E:\Study\Inflearn\projects\docker-lab

A. 쓰기 레이어는 컨테이너 것이다

  1. 1회차의 web은 지웠다. 같은 nginx 이미지로 새 컨테이너를 띄워 /tmp를 본다. --rm은 끝나면 컨테이너를 바로 지운다.

    docker run --rm nginx ls /tmp
    mark.txt가 보일까? 근거를 용어집 용어로 말한다.

B. 이름 없는 볼륨

  1. -v 없이 postgres를 띄운다. -e는 환경 변수를 넘긴다. postgres는 POSTGRES_PASSWORD가 없으면 뜨지 않는다.

    docker run -d --name pg0 -e POSTGRES_PASSWORD=pw postgres:18
docker volume ls
    -v를 안 줬다. docker volume ls에 무엇이 나올까?
  2. docker rm -f pg0
docker volume ls
    컨테이너를 지웠다. 그 볼륨은 남을까? 남는다면 나중에 누가 이 볼륨을 다시 찾아 쓸 수 있을까?

    확인한 뒤 남은 볼륨을 지운다. volume rm은 볼륨을 지운다. 이름은 volume ls에 나온 긴 문자열이다.

    docker volume rm <VOLUME NAME>

C. named volume — 오늘의 핵심

  1. -v pgdata:/var/lib/postgresql은 pgdata라는 볼륨을 postgres의 데이터 경로에 붙인다.

    docker run -d --name pg -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=docker_lab -v pgdata:/var/lib/postgresql postgres:18
docker volume ls
    pgdata를 미리 docker volume create로 만들지 않았다. 오류가 날까?

  2. 몇 초 기다린 뒤 테이블을 만든다. psql -U postgres -d docker_lab -c "SQL"은 postgres 사용자로 docker_lab DB에 접속해 SQL 한 줄을 실행한다. the database system is starting up이 나오면 다시 친다.

    docker exec pg psql -U postgres -d docker_lab -c "CREATE TABLE memo(t text); INSERT INTO memo VALUES ('hello');"

  3. 컨테이너를 지우고, 같은 명령으로 새로 만든다.

    docker rm -f pg
docker volume ls
docker run -d --name pg -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=docker_lab -v pgdata:/var/lib/postgresql postgres:18
docker exec pg psql -U postgres -d docker_lab -c "SELECT * FROM memo;"
    세 가지를 답한다. (1) rm -f 뒤 pgdata는 남을까? (2) 새 컨테이너의 ID는 지운 것과 같을까? (3) hello가 나올까? 두 번째 run에도 POSTGRES_DB를 줬는데, DB를 새로 만들어 덮어쓸까?

  4. volume inspect는 볼륨의 상세 정보를 JSON으로 보여 준다.

    docker volume inspect pgdata
    Mountpoint에 나온 경로를 Windows 탐색기에서 찾을 수 있을까? 그림의 어느 상자에 있는 경로일까?

D. bind mount

  1. site 폴더는 아직 없다. 그대로 nginx의 HTML 디렉터리에 bind mount한다. ${PWD}는 PowerShell의 현재 폴더 경로다. Get-ChildItem은 폴더 목록을 보여 준다.

    docker run -d --name web -p 8081:80 -v "${PWD}\site:/usr/share/nginx/html" nginx
Get-ChildItem
    호스트에 없는 경로를 줬다. 오류가 날까, site 폴더가 생길까? (문서는 생긴다고 한다. Windows에서도 그런지 직접 재 본다.) 이어서 통합 브라우저로 http://localhost:8081을 열면 1회차의 "Welcome to nginx!"가 보일까?

  2. 호스트에서 파일을 만들고 브라우저를 새로 고친다. Set-Content는 파일을 만들거나 덮어쓴다.

    Set-Content site\index.html "<h1>from host</h1>"
    컨테이너를 다시 만들지 않았다. 새로 고치면 바뀔까?

  3. 반대 방향. 컨테이너 안에서 파일을 만든다. sh -c "…"는 > 리다이렉트를 호스트가 아닌 컨테이너 안의 셸이 처리하게 한다.

    docker exec web sh -c "echo from-container > /usr/share/nginx/html/c.txt"
Get-ChildItem site
    호스트의 site에 c.txt가 보일까?
  4. docker rm -f web
Get-ChildItem site
    컨테이너를 지웠다. site의 파일들은 어떻게 될까?

5. 왜 docker-lab에서 bind mount가 느린가

projects\docker-lab은 Windows의 E: 드라이브에 있다. 그림처럼 데몬은 WSL 2 VM 안에 있으므로, 여기를 bind mount하면 파일을 읽고 쓸 때마다 VM 경계를 넘는다. Docker 문서는 Windows 드라이브에서 bind mount하면 I/O가 리눅스 파일 시스템보다 훨씬 느리고, 컨테이너가 파일 변경 이벤트(inotify)를 받지 못해 자동 리로드 도구가 제대로 돌지 않을 수 있다고 한다. 권장은 프로젝트를 WSL의 리눅스 파일 시스템에 두는 것이다. (Docker Desktop WSL 2 best practices)

6회차에 docker-lab을 dev container로 열 때, 같은 이유로 Gradle 캐시는 named volume에 둔다.
