5회차 · Compose

오늘의 성과: 4회차의 docker run 두 줄을 내가 쓴 compose.yaml 하나로 바꾸고, up 한 번으로 앱과 DB를 띄운다.

4회차에는 네트워크를 만들고, postgres를 띄우고, 앱을 띄우는 명령을 순서대로 쳤다. 오늘은 그 결과를 파일에 적어 두고 Compose가 맞춰 주게 한다. 6회차 dev container의 dockerComposeFile은 오늘 쓰는 compose.yaml을 그대로 읽는다. 용어는 용어집을 따른다.

1. 명령형에서 선언형으로

  • up을 다시 치면 Compose는 파일과 지금 상태를 비교한다. 설정이나 이미지가 바뀐 서비스만 컨테이너를 멈추고 다시 만든다. (docker compose up)
  • 그래서 같은 up을 여러 번 쳐도 된다. 바뀐 것이 없으면 아무것도 다시 만들지 않는다.

2. 프로젝트 이름과 리소스 이름

  • Compose가 만드는 것은 모두 하나의 프로젝트에 속한다. 기본 프로젝트 이름은 compose.yaml이 있는 폴더 이름이다. 소문자·숫자·-·_만 쓸 수 있다. (Specify a project name)
  • 프로젝트 이름은 -p 옵션, COMPOSE_PROJECT_NAME 환경 변수, 파일 맨 위의 name: 순서로 앞의 것이 이긴다. (Specify a project name)
  • Compose는 <프로젝트>_default라는 네트워크를 만들고 모든 서비스를 거기에 붙인다. 각 컨테이너는 그 네트워크에서 서비스 이름으로 찾을 수 있다. 3회차 사용자 정의 bridge의 이름 DNS와 같다. 이 네트워크는 이름 DNS가 없는 "기본 bridge"와 다르다. (Networking in Compose)
  • 볼륨에도 프로젝트 이름이 앞에 붙는다. 문서는 external 예시에서 Compose가 {project_name}_db-data라는 볼륨을 만들려 한다고 적는다. 그래서 같은 이름의 볼륨이 이미 있어도 Compose는 그것을 쓰지 않는다. (Volumes top-level element)
  • 이미 있는 볼륨을 쓰려면 external: true로 선언한다. Compose는 그 볼륨을 만들지 않고(Volumes), down으로 지우지도 않는다(compose down).
  • 컨테이너와 빌드한 이미지에 붙는 이름은 문서에서 찾지 못했다. 실습 B-4의 출력에서 확인한다.

3. depends_on과 healthcheck

  • depends_on: [db]처럼 짧게 쓰면 Compose는 db를 먼저 시작할 뿐이다. db가 요청을 받을 준비가 됐는지는 기다리지 않는다. (depends_on)
  • condition: service_healthy로 쓰면 db의 healthcheck가 통과할 때까지 app 시작을 미룬다. (depends_on)
  • healthcheck는 컨테이너 안에서 주기적으로 실행하는 확인 명령이다. 종료 코드 0이면 healthy, 1이면 unhealthy다. 처음 상태는 starting이다. (HEALTHCHECK)
필드뜻 (기본값)
test실행할 확인 명령. ["CMD-SHELL", "명령"]이면 셸로 실행한다. (healthcheck)
interval컨테이너 시작 후 첫 확인까지, 그리고 확인 사이의 간격 (30s)
timeout확인 한 번이 이보다 오래 걸리면 실패로 친다 (30s)
retries연속으로 이만큼 실패하면 unhealthy (3)
start_period시작 직후 이 기간의 실패는 retries에 세지 않는다 (0s)

필드 뜻과 기본값은 Dockerfile HEALTHCHECK에 있다. Compose의 healthcheck는 이 기본값을 따른다. postgres 이미지에 든 pg_isready는 서버가 접속을 받는지 확인해 받으면 0을 돌려준다. (pg_isready)

4. compose.yaml 쓰는 법

YAML 규칙은 네 가지만 알면 된다. (YAML 1.2 명세)

  • 키: 값. 콜론 뒤에 공백 한 칸.
  • 들여쓰기가 소속을 정한다. 공백만 쓴다(탭 금지). 같은 깊이는 같은 칸 수로 맞춘다.
  • 목록은 줄 앞에 - 를 붙인다.
  • # 뒤는 주석이다.

오늘 과제와 다른 앱(웹 + redis)으로 뼈대를 보인다. 키마다 4회차 docker run의 어느 옵션에 해당하는지 주석을 달았다.

services:                 # 컨테이너 정의들
  web:                    # 서비스 이름 = DNS 이름
    build: .              # docker build .
    ports:
      - "8000:5000"       # -p 8000:5000
    environment:
      CACHE_HOST: cache   # -e CACHE_HOST=cache
    # cache가 healthy가 될 때까지 기다린 뒤 시작
    depends_on:
      cache:
        condition: service_healthy

  cache:
    image: redis:7        # 이미지 이름
    volumes:
      - cachedata:/data   # -v cachedata:/data
    # 준비 확인: 5초마다 컨테이너 안에서 실행
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s

volumes:                  # services와 같은 깊이
  cachedata:              # named volume 선언
  • --name과 --network에 해당하는 줄이 없다. 컨테이너 이름은 Compose가 붙이고, 네트워크는 Compose가 만드는 <프로젝트>_default 네트워크를 쓴다.
  • environment는 위처럼 맵으로도, - CACHE_HOST=cache처럼 목록으로도 쓸 수 있다. (environment)
  • 키 전체 목록과 각 키의 문법은 Services top-level element에 있다. 쓰고 나면 docker compose config가 문법 오류를 알려 준다.

실무에서는 빈 파일에서 시작하기보다 공식 문서 예제나 이미 쓰던 파일을 고쳐 쓴다. docker init은 Dockerfile·compose.yaml·.dockerignore 초안을 만들어 주지만, Java 템플릿은 Maven 프로젝트용이고 만든 뒤 프로젝트에 맞게 고쳐야 한다고 문서가 적고 있다. (docker init) 어느 경우든 파일을 읽고 고칠 줄 알아야 한다.

5. 오늘 쓰는 명령

명령하는 일
docker compose config파일을 읽어 기본값까지 채운 최종 설정을 출력한다. 아무것도 만들지 않는다. (compose config)
docker compose up -d필요한 이미지를 빌드·pull하고 네트워크·볼륨·컨테이너를 만들어 시작한다. -d는 1회차와 같이 백그라운드 실행이다. (compose up)
up --build시작 전에 이미지를 빌드한다. 앱 코드를 고친 뒤 쓴다. (compose up)
docker compose ps이 프로젝트의 컨테이너만 보여 준다. -a를 붙이면 멈춘 것도 보인다. (compose ps)
docker compose logs 서비스서비스 컨테이너의 로그. -f는 1회차처럼 따라 읽는다. (compose logs)
docker compose exec 서비스 명령실행 중인 서비스 컨테이너 안에서 명령을 실행한다. 1회차 docker exec와 같고, 컨테이너 이름 대신 서비스 이름을 쓴다. (compose exec)
docker compose down이 프로젝트의 컨테이너와 네트워크를 지운다. (compose down)
docker network ls네트워크 목록. 볼륨 목록을 보는 docker volume ls와 같은 꼴이다. (network ls)
down -v파일의 volumes:에 선언한 named volume도 지운다. external 볼륨은 지우지 않는다. (compose down)

6. 실습 — 예측하고 직접 친다

PowerShell(lab 터미널)의 projects/docker-lab에서 친다. 명령마다 예측을 먼저 말하고, Clear-Host 후 실행한 뒤 @terminal:lab으로 보여 준다.

A. 준비 (예측 없음)

  1. Docker Desktop을 켠다. Dockerfile에 RUN sleep 15 … 줄이 남아 있으면 지운다(이미 지웠으면 건너뛴다). 4회차의 app·pg 컨테이너는 지운다. app이 호스트 8081을 잡고 있다.

    cd E:\Study\Inflearn\projects\docker-lab
docker rm -f app pg

  2. projects/docker-lab/compose.yaml을 직접 쓴다. 출발점은 4회차에 친 두 줄이다. 아래는 그 명령이다.

    docker run -d --name pg --network labnet -e POSTGRES_PASSWORD=pw -v pgdata:/var/lib/postgresql postgres:18
docker run -d --name app --network labnet -p 8081:8080 -e SPRING_DATASOURCE_URL=jdbc:postgresql://pg:5432/docker_lab docker-lab:1

    명령을 조각으로 나눠 어디로 가는지 적었다. 4절의 뼈대와 이 표만 보고 쓸 수 있다. 오늘 새로 더하는 것은 새로로 표시했다.

    조각뜻compose.yaml에서
    DB (첫 줄)
    --name pg컨테이너 이름. 앱이 이 이름으로 DB를 찾았다services: 아래 서비스 이름 db:. 이름이 pg에서 db로 바뀐다
    postgres:18쓸 이미지image: postgres:18
    -e POSTGRES_PASSWORD=pwpostgres 관리자 비밀번호environment: 아래 POSTGRES_PASSWORD: pw
    새로처음 뜰 때 만들 DB 이름. 새 볼륨에는 docker_lab DB가 없다 (postgres 이미지)environment: 아래 POSTGRES_DB: docker_lab
    -v pgdata:/var/lib/postgresqlnamed volume pgdata를 postgres 18의 데이터 경로에 붙인다volumes: 아래 - pgdata:/var/lib/postgresql. 그리고 파일 맨 아래(services:와 같은 깊이) volumes: 아래 pgdata:
    새로DB가 접속을 받는지 5초마다 확인 (3절)healthcheck: 아래 test: ["CMD-SHELL", "pg_isready -U postgres -d docker_lab"], interval: 5s
    앱 (둘째 줄)
    --name app컨테이너 이름서비스 이름 app:
    docker-lab:14회차에 이 폴더에서 docker build -t docker-lab:1 .로 만든 이미지build: . (이 폴더의 Dockerfile로 빌드)
    -p 8081:8080호스트 8081 → 앱 8080ports: 아래 - "8081:8080"
    -e SPRING_DATASOURCE_URL=…앱이 접속할 DB 주소. 호스트 부분이 DB 컨테이너 이름이다environment: 아래 SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/docker_lab. pg가 db로 바뀐다
    새로db가 healthy가 된 뒤 시작depends_on: → db: → condition: service_healthy (세 단계 들여쓰기)

    -d백그라운드 실행파일에 없다. docker compose up -d의 옵션이다

    맨 위 version:은 적지 않는다. 지금은 쓰지 않는 필드라 경고만 나온다. (Version and name)

B. 처음 올리기

  1. 파일을 읽어 기본값까지 채운 최종 설정을 출력한다. 아무것도 만들지 않는다.

    docker compose config
    맨 위 name:에 무엇이 나올까? 파일에 적지 않은 네트워크가 출력에 나올까, 나온다면 어떤 이름일까?

  2. 파일대로 이미지를 빌드하고 네트워크·볼륨·컨테이너를 만들어 백그라운드로 시작한다.

    docker compose up -d
    만들어지는 네트워크와 볼륨은 각각 어떤 이름일까? db와 app 중 어느 쪽이 먼저 시작을 마칠까? 왜?

    컨테이너와 이미지에 붙은 이름은 출력에서 확인한다.

  3. 이 프로젝트의 컨테이너 목록과 전체 볼륨 목록을 본다.

    docker compose ps
docker volume ls
    db의 STATUS에는 무엇이 붙어 있을까? 2회차부터 써 온 pgdata 볼륨을 이 db가 쓰고 있을까?

  4. 통합 브라우저로 http://localhost:8081을 연다. 이전 페이지가 캐시에 남아 있을 수 있으니 Ctrl+Shift+R로 새로 고친다.

    브라우저에 무엇이 보일까? 왜?

    확인한 뒤 앱 로그를 읽는다.

    docker compose logs app

    그다음 db 컨테이너 안에서 psql로 memo 테이블을 만들고 한 줄 넣는다. -c는 뒤의 SQL을 실행하고 끝낸다는 뜻이다.

    docker compose exec db psql -U postgres -d docker_lab -c "CREATE TABLE memo (t text); INSERT INTO memo VALUES ('hello compose');"

C. 다시 up

  1. 파일을 바꾸지 않고 다시 친다.

    docker compose up -d
    컨테이너를 다시 만들까? 출력 줄에 어떤 상태가 찍힐까?

D. down과 down -v

  1. 컨테이너와 네트워크를 지운다. 이어서 남은 것을 본다.

    docker compose down
docker compose ps -a
docker volume ls
docker network ls
    컨테이너·네트워크·볼륨 중 무엇이 남을까? 다시 docker compose up -d 하면 브라우저에 hello compose가 나올까?

    예측을 말한 뒤 docker compose up -d로 올려 브라우저에서 확인한다.

  2. 이번에는 선언한 볼륨까지 지우고 다시 올린다.

    docker compose down -v
docker volume ls
docker compose up -d
    이번에는 무엇이 지워질까? 다시 올린 뒤 브라우저에는 무엇이 나올까?

7. 정리와 남겨 둘 것

2~3회차에 손으로 만든 pgdata와 labnet은 이제 아무도 쓰지 않는다. 지운다.

docker volume rm pgdata
docker network rm labnet

compose.yaml과 프로젝트의 컨테이너·볼륨은 남긴다. 6회차 dev container가 이 파일로 app과 db를 띄운다.
