3회차 · 네트워크

오늘의 성과: 포트를 publish하지 않은 postgres에 다른 컨테이너가 pg라는 이름으로 접속해 2회차의 hello를 읽는다.

4회차에 만드는 앱 컨테이너는 DB 주소가 필요하다. IP는 컨테이너를 다시 만들 때마다 바뀔 수 있으므로 이름으로 찾아야 한다. 5회차 Compose의 서비스 이름 접속도 오늘 배우는 기능 위에서 돈다. 용어는 용어집을 따른다.

1. 컨테이너에 닿는 두 길

2. publish와 EXPOSE

  • -p 8081:80은 호스트의 8081을 컨테이너의 TCP 80에 연결한다. 호스트 쪽이 앞이다. (Port publishing)
  • 호스트 주소를 생략하면 호스트의 모든 주소(0.0.0.0, [::])에 publish된다. 문서는 "포트 publish는 기본적으로 안전하지 않다"고 경고한다. 호스트에서만 쓰려면 -p 127.0.0.1:8081:80처럼 주소를 붙인다. (Port publishing)
  • Dockerfile의 EXPOSE는 실제로 publish하지 않는다. 이미지를 만든 사람이 "이 포트를 쓴다"고 적어 두는 문서 역할이다. (Dockerfile reference — EXPOSE)
  • -P(대문자)는 EXPOSE된 포트를 전부 호스트의 무작위 높은 번호 포트에 publish한다. (run --publish-all)

3. 기본 bridge와 사용자 정의 bridge

--network를 주지 않은 컨테이너는 전부 기본 bridge 네트워크에 붙는다. 1·2회차의 컨테이너도 모두 여기 있었다. (Bridge — default bridge)

기본 bridge사용자 정의 bridge (network create)
서로 찾는 법IP로만. 이름은 legacy --link로만컨테이너 이름이나 별칭으로 (자동 DNS)
누가 같이 있나--network 없이 띄운 모든 컨테이너. 상관없는 것끼리도 통신한다그 네트워크에 붙인 컨테이너만
붙이고 떼기빼려면 멈추고 다른 옵션으로 다시 만든다실행 중에 network connect / disconnect

같은 사용자 정의 bridge에 있는 컨테이너끼리는 모든 포트가 서로 열려 있다. -p는 다른 네트워크나 호스트 밖에서 들어올 때만 필요하다.

근거: Bridge — Differences between user-defined bridges and the default bridge.

2회차와 비교. 마운트는 create 때 정해져서 바꾸려면 컨테이너를 다시 만들어야 했다. 사용자 정의 네트워크는 실행 중인 컨테이너에 붙였다 뗄 수 있다.

4. 오늘 쓰는 명령

명령하는 일
run -p 호스트:컨테이너호스트 포트를 컨테이너 포트에 publish한다. (run -p)
run -PEXPOSE된 포트를 모두 무작위 호스트 포트에 publish한다.
run --network 이름컨테이너를 그 네트워크에 붙여 만든다. (run --network)
port 컨테이너그 컨테이너의 포트 매핑을 보여 준다. (docker port)
image inspect -f-f "{{json .Config.ExposedPorts}}": 이미지 설정 중 EXPOSE된 포트만 JSON으로 뽑는다. -f는 출력 형식(Go 템플릿)을 정한다. (docker inspect)
network create 이름사용자 정의 bridge 네트워크를 만든다. 드라이버 기본값이 bridge다. (network create)
network inspect 이름네트워크 상세. Containers에 붙은 컨테이너와 IP가 나온다.
network connect실행 중인 컨테이너를 네트워크에 붙인다. (network connect)
psql -h 주소-e PGPASSWORD=pw로 넘긴 값을 psql이 비밀번호로 읽고, -h로 준 주소의 서버에 접속한다. (libpq 환경 변수)

5. 실습 — 예측하고 직접 친다

PowerShell(lab 터미널)에서 친다. 명령마다 예측을 먼저 말하고, Clear-Host 후 실행한 뒤 @terminal:lab으로 보여 준다.

A. publish와 EXPOSE

  1. -p 없이 nginx를 띄운다.

    docker run -d --name web nginx
docker ps
    PORTS 칸에 무엇이 나올까? 통합 브라우저로 http://localhost:80을 열면 Welcome 페이지가 보일까?

  2. nginx 이미지에 적힌 EXPOSE를 본다.

    docker image inspect -f "{{json .Config.ExposedPorts}}" nginx
    우리는 포트를 지정한 적이 없다. 무엇이 나올까? 1번의 PORTS 칸과 어떤 관계일까?

  3. publish해서 다시 만든다. docker port는 포트 매핑을 보여 준다.

    docker rm -f web
docker run -d --name web -p 8081:80 nginx
docker port web
    docker port는 몇 줄을 출력할까? 호스트 쪽 주소에는 무엇이 찍힐까? 이번엔 http://localhost:8081이 열릴까?

  4. -P(대문자)로 하나 더 띄운다.

    docker run -d --name web2 -P nginx
docker port web2
    호스트 포트는 몇 번이 될까? 이 포트 번호는 어디서 정해졌을까?

    확인한 뒤 지운다.

    docker rm -f web web2

B. 기본 bridge에는 이름이 없다

  1. 2회차의 pgdata를 붙여 postgres를 띄운다. -p는 주지 않는다. 이미 초기화된 볼륨이라 비밀번호는 pw, DB는 docker_lab 그대로다.

    docker run -d --name pg -e POSTGRES_PASSWORD=pw -v pgdata:/var/lib/postgresql postgres:18

  2. 다른 컨테이너에서 이름으로 접속한다. 클라이언트도 postgres:18 이미지를 쓴다. 그 안의 psql만 빌려 쓰고 --rm으로 바로 지운다.

    docker run --rm -e PGPASSWORD=pw postgres:18 psql -h pg -U postgres -d docker_lab -c "SELECT * FROM memo;"
    두 컨테이너는 모두 기본 bridge에 있다. hello가 나올까? 실패한다면 어느 단계(이름 찾기, 연결, 인증)에서 실패할까?

  3. 기본 bridge에 붙은 컨테이너의 IP를 본다.

    docker network inspect bridge

    Containers 아래 pg의 IPv4Address에서 /16 앞부분을 쓴다.

    docker run --rm -e PGPASSWORD=pw postgres:18 psql -h <pg의 IP> -U postgres -d docker_lab -c "SELECT * FROM memo;"
    IP로는 될까? 된다면 이 방법을 4회차 앱 설정에 그대로 쓰면 무엇이 문제일까?

C. 사용자 정의 bridge — 오늘의 핵심

  1. 네트워크를 만들고, 실행 중인 pg를 붙인다.

    docker network create labnet
docker network connect labnet pg
docker network inspect labnet
    pg를 다시 만들지 않았다. connect가 성공할까? 이제 pg는 네트워크 몇 개에 붙어 있을까?

  2. 클라이언트를 labnet에 붙여 이름으로 접속한다.

    docker run --rm --network labnet -e PGPASSWORD=pw postgres:18 psql -h pg -U postgres -d docker_lab -c "SELECT * FROM memo;"
    pg는 5432를 publish하지 않았다. hello가 나올까? 근거를 3절의 표로 말한다.

6. 남겨 둘 것

4회차에 앱 컨테이너를 labnet에 붙여 pg에 접속시킨다. labnet과 pgdata는 지우지 않는다. 5회차 Compose로 옮길 때 정리한다.

더 읽을 것
