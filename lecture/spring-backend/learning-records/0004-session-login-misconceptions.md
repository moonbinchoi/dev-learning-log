# 세션 로그인: 흐름은 추적했고, 쿠키와 서버 세션의 경계는 실행 결과로 바로잡혔다

2회차에서 틀린 비밀번호 요청의 흐름을 스스로 추적하고 누가 검사하고 누가 분기하는지 답했다. 반면 "쿠키 쪽 상태"와 "서버 세션 쪽 상태"를 구분하는 데 반복해서 흔들렸다. 3회차의 필터와 인터셉터는 세션을 읽는 코드이므로, 이 경계를 다시 확인하고 시작한다.

## Evidence
- 진단: 쿠키에 `memberId`를 담으면 값 조작이 가능하다는 것, `jakarta.annotation.PostConstruct`는 알았다. 정보 탈취와 훔친 쿠키 재사용, `getSession(false)`, 타임아웃 기준과 기본값은 몰랐다. 세션 방식에서 서버가 가진 것을 "세션 ID"로만 답했다(실제는 세션 ID → 세션 객체 표).
- 직접 추적(틀린 비밀번호 `POST /login`): ②③에서 무슨 일이 일어나는지, ④⑤가 일어나지 않는다는 것, 세션 저장소와 쿠키가 비어 있다는 것을 맞혔다. "검사는 Validator와 `LoginService`, 분기는 컨트롤러"도 맞혔다. `reject()`를 `LoginService`가 부른다고 한 것은 컨트롤러라고 바로잡혔다.
- 실행 전 예측에서 틀린 것과 실행 결과로 바로잡힌 것:
  - 로그인 응답의 쿠키 이름을 `loginMember`로 예측했다(실제 `JSESSIONID`, `loginMember`는 세션 속성 이름). 상태 코드는 `302`.
  - 임의 `JSESSIONID`로 `GET /`을 보내면 "리다이렉트"라고 예측했다(실제 `200` `home`, `Set-Cookie` 없음).
  - 로그아웃 뒤 쿠키 파일이 "`invalidate()`되어 달라진다"고 예측했다(실제 전후 동일. `invalidate()`는 서버 세션만 지운다). 홈이 `home`이 되는 것은 맞혔다.
- 코드 결함 6건이 채점에서 나왔다. 개념과 연결된 것: 뷰 이름을 URL(`"/"`, `"/home"`)로 썼다(뷰 이름은 템플릿 파일 이름), `model.addAttribute(객체)`의 기본 이름이 `memberSaveForm`이라는 것을 몰랐다, 세션에서 받은 회원을 저장소에서 다시 찾았다.
- 타임아웃: 기준이 마지막 요청 시각이라는 이유를 예측에서 스스로 말했다(① 1분 방치 → `home`, ② 30초마다 새로고침 → `loginHome`). 실험은 실행하지 않고 정답만 받았다.
- 면접 Q1은 "세션이 쿠키를 감싼다"로 뒤집어 답했고 설명 뒤 바로잡혔다. Q2, Q3은 통과했다(Q2는 메모리와 타임아웃 길이 주의가 빠짐).
- 회원 가입 폼 객체와 `Member`를 나누는 이유를 의존 방향(`web` → `domain`), 모양 차이, 호출자 다양성으로 설명받았고, 폼에 `toMember()`를 두는 설계를 직접 골랐다.

## Implications
- 3회차 회상 퀴즈에 "`invalidate()`가 지우는 것", "쿠키 이름과 세션 속성 이름", "임의 쿠키로 `GET /`"을 낸다.
- 필터에서 `getSession(false)`를 쓰는 이유를 코딩 전에 먼저 말하게 한다. 진단에서 몰랐고 코드로 확인하지 않았다.
- 실행 전 예측에서 "서버에 있는 것"과 "브라우저에 있는 것"을 구분해 말하게 하는 질문을 넣는다. 결과를 보고서야 바로잡히는 경향이 있다.
