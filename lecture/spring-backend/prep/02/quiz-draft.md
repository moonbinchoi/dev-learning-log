# 2회차 퀴즈 초안

## 회상 퀴즈
- Q: 검증에 실패했을 때 컨트롤러는 왜 리다이렉트하지 않고 폼 뷰 이름을 그대로 반환하는가?
  - 모범 답: 리다이렉트는 브라우저가 보내는 새 요청이라 지금 요청의 모델과 `BindingResult`(입력값·오류)가 사라진다. 뷰를 바로 그리면 모델에 담긴 `BindingResult`로 입력값과 오류 메시지를 함께 그릴 수 있다. 오류를 걸러 내는 것은 `BindingResult`가 아니라 컨트롤러의 `hasErrors()` 분기다.
- Q: `Item` 필드에 `@NotBlank`를 달면 상품 등록 때 검증되는가?
  - 모범 답: 컨트롤러 파라미터에 `@Validated`(또는 `@Valid`)가 붙은 객체만 검증된다. 등록 메서드가 `ItemSaveForm`을 받으면 `Item`의 애너테이션은 실행되지 않는다. 애너테이션은 규칙 선언일 뿐 스스로 검사하지 않는다.
- Q: 가격 칸에 `abc`를 넣었을 때 `BindingResult`가 있을 때와 없을 때 결과와 상태 코드는?
  - 모범 답: 있으면 컨트롤러가 호출되고 `typeMismatch` 오류가 담겨 폼이 다시 그려진다(200). 없으면 바인딩 예외가 나고 컨트롤러가 호출되지 않으며 400 오류 페이지가 뜬다. 400은 클라이언트 입력 문제, 500은 서버 코드 문제다.
- Q: `redirectAttributes.addAttribute("status", true)`의 값은 `redirect:/items/{itemId}`에서 URL의 어디로 가는가?
  - 모범 답: URL에 `{status}` 자리가 없으므로 쿼리 파라미터로 붙는다. `/items/1?status=true`. `itemId`는 `{itemId}` 자리를 채운다.

## 진단 질문
- Q: 쿠키에 `memberId=1`을 그대로 담아 로그인을 유지하면 어떤 보안 문제가 생기는가? 세 가지.
  - 모범 답: 사용자가 쿠키 값을 바꿔 다른 회원이 될 수 있다. 쿠키는 브라우저와 네트워크에 노출되므로 담긴 정보를 훔칠 수 있다. 한 번 훔친 쿠키를 계속 쓸 수 있다.
- Q: 세션 방식으로 로그인했을 때 브라우저와 서버는 각각 무엇을 가지고 있는가?
  - 모범 답: 브라우저는 `JSESSIONID` 쿠키(추측할 수 없는 세션 ID)만 가진다. 서버는 세션 저장소에 세션 ID → 세션 객체를 두고, 그 세션에 로그인 회원을 넣어 둔다.
- Q: `request.getSession()`과 `request.getSession(false)`의 차이는? 홈 화면에서 앞의 것을 쓰면 무엇이 문제인가?
  - 모범 답: `getSession()`(= `true`)은 세션이 없으면 새로 만들고, `false`는 없으면 `null`을 돌려준다. 홈에서 `getSession()`을 쓰면 로그인하지 않은 방문자마다 쓸모없는 세션이 생겨 메모리를 차지한다.
- Q: 세션 타임아웃은 무엇을 기준으로 재는가? 기본값은?
  - 모범 답: 세션 생성 시각이 아니라 마지막 요청 시각이다. 그 세션 ID를 실은 요청이 오면 다시 잰다. 기본 30분(1800초).
- Q: Spring Boot 4에서 `@PostConstruct`는 어느 패키지에서 import하는가? 교재처럼 쓰면 어떻게 되는가?
  - 모범 답: `jakarta.annotation.PostConstruct`. Spring Framework 7이 `javax.annotation` 지원을 없앴으므로 교재의 `javax.annotation.PostConstruct`는 컴파일되지 않는다.

## 면접 질문
- Q: 로그인 상태를 쿠키에 직접 저장하지 않고 세션을 쓰는 이유는 무엇인가? 세션도 쿠키를 쓰는데 무엇이 다른가?
  - 모범 답: 쿠키는 클라이언트에 있어 바꾸거나 훔칠 수 있다. 세션은 회원 정보를 서버에 두고, 쿠키에는 추측할 수 없는 세션 ID만 담는다. 그래서 값을 바꿔도 다른 사용자가 될 수 없고, ID를 훔쳐도 정보가 없으며, 서버가 만료 시간이나 강제 삭제로 훔친 ID를 무효로 만들 수 있다. 쿠키는 ID 전달 수단으로만 쓴다.
- Q: 사용자가 로그아웃하지 않고 브라우저를 닫으면 서버의 세션은 어떻게 되는가? 그래서 무엇을 조심해야 하는가?
  - 모범 답: HTTP는 요청마다 연결이 끊기므로 서버는 사용자가 떠났는지 모른다. 마지막 요청 뒤 타임아웃(기본 30분)이 지나야 세션이 지워진다. 세션은 서버 메모리에 쌓이므로(데이터 크기 × 사용자 수) 꼭 필요한 데이터만 넣고, 시간을 너무 길게 잡지 않는다.
- Q: `JSESSIONID`를 다른 사람이 가로채면 어떤 일이 생기고, 서버는 피해를 어떻게 줄이는가?
  - 모범 답: 세션이 살아 있는 동안 그 사람으로 요청할 수 있다. 세션 안의 정보 자체는 쿠키에 없으므로 빼 가지는 못한다. 서버는 타임아웃을 짧게 두고, 의심되면 그 세션을 서버에서 지워(`invalidate`) 피해 시간을 줄인다.
