3회차 · 로그인 체크: 필터와 인터셉터

스프링 MVC 2편 7장 · Spring Boot 4.1.1 · 용어는 용어집

오늘의 결과물. 로그인하지 않은 사용자가 /items 주소를 직접 쳐도 상품 화면에 들어가지 못하고 로그인 화면으로 간다. 로그인에 성공하면 처음 열려던 주소로 돌아간다. 로그인 검사는 컨트롤러마다 쓰지 않고 한곳에 둔다. 처음에는 서블릿 필터로 만들고, 같은 일을 스프링 인터셉터로 바꾼다. 마지막으로 홈 화면 컨트롤러가 @Login Member 파라미터 하나로 로그인 회원을 받게 한다.

2회차에서는 홈 화면에만 상품 관리 버튼을 숨겼다. 주소를 직접 치면 그대로 들어간다 (교재 7장 18–24줄). 면접에서는 "필터와 인터셉터는 무엇이 다른가"를 묻는다.

1. 동작 원리: 로그인하지 않은 사용자의 GET /items

로그인하지 않은 사용자가 상품 목록을 열면 요청이 네 번 오간다. ① 첫 GET /items는 로그인 체크에 막혀 로그인 화면 주소를 응답으로 받는다. ⑤ 브라우저가 그 주소로 로그인 폼을 받는다. ⑥ 로그인 요청이 세션을 만든 뒤 원래 주소로 보내 주고, ⑦ 다시 보낸 GET /items는 검사를 통과한다. 아래 흐름은 오늘 마지막에 완성하는 인터셉터 버전이다. 필터 버전도 순서는 같고, ②③의 검사가 DispatcherServlet보다 앞에서 일어난다는 점만 다르다.

등장 객체역할
브라우저받은 JSESSIONID 쿠키를 보관해 요청마다 싣는다. 리다이렉트 응답을 받으면 Location의 주소로 새 GET을 보낸다.
톰캣(WAS)WAS(웹 애플리케이션 서버)는 HTTP 요청을 받아 자바 코드(서블릿)를 실행해 주는 서버이고, 스프링 부트는 톰캣을 내장해 쓴다. 톰캣은 요청을 받아 필터 체인을 거쳐 DispatcherServlet에 넘긴다. 세션 저장소(세션 ID → 세션 객체)도 톰캣 메모리에 있다.
DispatcherServlet스프링 MVC의 입구. 요청 주소를 처리할 컨트롤러 메서드(핸들러)를 찾고, 그 메서드를 부르기 전에 인터셉터의 preHandle을 등록 순서대로 부른다. 하나라도 false를 돌려주면 컨트롤러를 부르지 않는다.
LogInterceptor등록 순서 1번 인터셉터. 요청마다 로그를 남기고 항상 true를 돌려준다. 검사는 하지 않는다.
LoginCheckInterceptor등록 순서 2번 인터셉터. 검사하고 분기한다. 세션에 loginMember가 없으면 /login?redirectURL=원래경로로 리다이렉트 응답을 정하고 false를 돌려준다. 있으면 true.
LoginController로그인 성공 뒤 쿼리 파라미터 redirectURL의 경로로 리다이렉트한다. 값이 없으면 /로 간다.
ItemController로그인 검사 코드가 없다. 인터셉터가 true를 돌려준 요청만 받는다.

① 요청브라우저가 GET /items를 보낸다. 로그인한 적이 없어 쿠키가 없다.없음비어 있음
② 핸들러 찾기톰캣이 요청을 DispatcherServlet에 넘긴다. DispatcherServlet은 /items를 처리할 핸들러로 ItemController의 목록 메서드를 찾고, 부르기 전에 인터셉터의 preHandle을 순서대로 부른다. 1번 LogInterceptor는 로그를 남기고 true를 돌려준다.없음비어 있음
③ 로그인 체크2번 LoginCheckInterceptor가 request.getSession(false)를 부른다. 요청에 쿠키가 없으니 null이다. response.sendRedirect("/login?redirectURL=/items")로 응답을 정하고 false를 돌려준다. DispatcherServlet은 컨트롤러를 부르지 않는다.없음비어 있음
④ 응답상태 302, Location: /login?redirectURL=/items로 응답한다. 세션을 만들지 않았으니 Set-Cookie는 없다.없음비어 있음
⑤ 로그인 폼브라우저가 Location의 주소로 GET을 보낸다. /login은 LoginCheckInterceptor의 제외 경로라 검사 없이 LoginController가 로그인 폼을 그린다. 주소창에는 ?redirectURL=/items가 남아 있다.없음비어 있음
⑥ 로그인test / test!로 폼을 제출하면 POST /login?redirectURL=/items가 간다. LoginController가 검증과 로그인 검사를 마치고 request.getSession()으로 새 세션을 만들어 loginMember를 넣는다. 파라미터로 받은 redirectURL 값 /items로 "redirect:/items"를 반환한다. 새 세션이 생겼으니 톰캣이 Set-Cookie: JSESSIONID=ABC…를 붙인다.JSESSIONID=ABC… 저장ABC… → loginMember=회원 test
⑦ 다시 상품 목록브라우저가 GET /items에 Cookie: JSESSIONID=ABC…를 싣는다. LoginCheckInterceptor가 getSession(false)로 세션을 찾고, 그 안에 loginMember가 있으니 true를 돌려준다. DispatcherServlet이 ItemController를 불러 상품 목록을 그린다.JSESSIONID=ABC…같음

검사도 분기도 LoginCheckInterceptor 한곳이 한다. 상품 컨트롤러가 늘어도 로그인 검사 코드는 늘지 않고, 로그인 정책이 바뀌면 이 한곳만 고친다 (교재 7장 24–26줄, 330줄). 여러 기능이 공통으로 필요로 하는 이런 일을 공통 관심사라고 한다.

⑥에서 로그인 폼이 쿼리 파라미터 redirectURL까지 함께 보내는지는 공식 문서에서 찾지 못했다. 폼의 <form>에는 th:action이 값 없이 붙어 있다. 7절 A-4에서 브라우저로 직접 확인한다.

2. 필터와 인터셉터는 어디에 끼어드는가

필터는 서블릿이 제공하는 기술이고, 인터셉터는 스프링 MVC가 제공하는 기술이다. 둘 다 웹의 공통 관심사를 처리하지만 끼어드는 위치가 다르다 (교재 7장 340–349줄).

HTTP 요청 -> WAS -> 필터 -> 서블릿(DispatcherServlet) -> 스프링 인터셉터 -> 컨트롤러
  • 브라우저가 보낸 요청
  • 서버 처리
  • 컨트롤러
  • 요청을 막고 끝냄
서블릿 필터스프링 인터셉터
제공서블릿 표준(jakarta.servlet.Filter)스프링 MVC(HandlerInterceptor)
위치DispatcherServlet 앞DispatcherServlet 뒤, 컨트롤러 호출 직전 (교재 7장 348줄)
요청을 막는 법chain.doFilter()를 부르지 않고 return (교재 7장 136–137, 262줄)preHandle이 false를 반환 (교재 7장 400줄)
호출 시점doFilter 하나. 그 안에서 chain.doFilter() 앞뒤에 코드를 둔다preHandle(컨트롤러 전), postHandle(컨트롤러 후), afterCompletion(뷰 렌더링 후)로 나뉜다 (교재 7장 390줄)
받는 정보request, response그에 더해 호출될 핸들러(handler)와 ModelAndView (교재 7장 391줄)
경로 지정addUrlPatterns에 서블릿 URL 패턴(/*)으로 적용할 곳을 정한다 (교재 7장 170–174줄). 오늘 코드는 뺄 경로를 필터 안의 화이트리스트로 거른다 (교재 7장 257줄)addPathPatterns, excludePathPatterns로 넣을 곳과 뺄 곳을 등록한다 (교재 7장 525, 632줄)
필터만 되는 것chain.doFilter(request, response)에 다른 request·response 객체를 넘겨 바꿔치기할 수 있다 (교재 7장 334줄)안 된다

교재의 결론은 "스프링 MVC를 사용하고, 특별히 필터를 꼭 사용해야 하는 상황이 아니라면 인터셉터를 사용하는 것이 더 편리하다"이다 (교재 7장 421줄).

인터셉터의 세 메서드는 언제 불리는가

  • preHandle이 false를 돌려주면 뒤의 인터셉터와 핸들러 어댑터가 호출되지 않는다 (교재 7장 400줄).
  • afterCompletion은 핸들러 실행 결과와 상관없이 불린다. 다만 그 인터셉터 자신의 preHandle이 true를 돌려준 경우에만 불린다 (HandlerInterceptor API, afterCompletion 항목).
  • 그래서 요청이 끝났다는 로그처럼 예외와 상관없이 해야 하는 일은 postHandle이 아니라 afterCompletion에 둔다 (교재 7장 416, 499줄).

3. 핵심 요약

코드·설정동작
chain.doFilter(request, response)다음 필터가 있으면 그 필터를, 없으면 서블릿을 부른다. 부르지 않으면 다음 단계로 진행하지 않는다 (교재 7장 136–137줄).
response.sendRedirect(주소) 뒤 return;필터에서 리다이렉트 응답을 정하고 끝낸다. 뒤의 필터, 서블릿, 컨트롤러가 모두 호출되지 않는다 (교재 7장 262줄).
preHandle에서 return false;인터셉터에서 같은 일을 한다. 리다이렉트는 return false 앞에서 response.sendRedirect로 정한다 (교재 7장 593–594줄).
request.getSession()getSession(true)와 같다. 세션이 있으면 그것을, 없으면 새로 만들어 돌려준다. 새로 만들면 톰캣이 응답에 Set-Cookie: JSESSIONID=…를 붙인다(2회차 실행 결과).
request.getSession(false)세션이 있으면 그것을, 없으면 null을 돌려준다. 새로 만들지 않는다 (Servlet 6.1 API). 2회차에서 모르는 JSESSIONID를 보냈을 때도 "세션 없음"으로 처리됐다.
화이트리스트인증과 상관없이 항상 허용하는 경로 목록. 필터는 이 목록을 코드로 들고 있다가 목록에 없는 경로만 검사한다. 홈, 회원 가입, 로그인, CSS는 로그인 전에도 열려야 한다 (교재 7장 257줄).
"/login?redirectURL=" + requestURI막힌 요청의 경로를 쿼리 파라미터로 로그인 화면에 넘긴다. 로그인에 성공하면 LoginController가 그 경로로 돌려보낸다 (교재 7장 261, 322줄).
@Login Member member직접 만든 ArgumentResolver가 세션의 로그인 회원을 꺼내 파라미터에 넣는다. 세션이 없으면 null이다 (교재 7장 666줄).

4. Boot 4.1 차이

  • 필터 쪽 타입은 모두 jakarta.servlet에서 import한다: Filter, FilterChain, ServletRequest, ServletResponse, ServletException, jakarta.servlet.http.*. 교재 코드는 javax.servlet을 쓴다 (교재 7장 206–209줄). Boot 4.1은 Servlet 6.1 기반이다 (Boot: System Requirements).
  • Servlet 6.1의 Filter에서 init과 destroy는 default 메서드다. doFilter만 구현하면 된다 (Servlet 6.1: Filter).
  • FilterRegistrationBean의 패키지는 그대로 org.springframework.boot.web.servlet이다 (Boot API: FilterRegistrationBean).
  • HandlerInterceptor의 세 메서드는 모두 default다. 필요한 메서드만 구현한다 (HandlerInterceptor API).
  • 인터셉터 경로 패턴은 PathPattern 문법을 따른다 (InterceptorRegistration API). PathPattern에서 **는 패턴 끝에만 쓸 수 있다. /pages/**/details 같은 패턴은 쓰지 않는다 (PathPattern API). 오늘 쓰는 /**, /css/**, /*.ico는 이 조건에 맞는다.
패턴뜻 (교재 7장 546–551줄)
?한 글자
*경로 한 칸(/와 / 사이) 안의 0개 이상 글자. /*.ico는 /favicon.ico에 맞고 /a/favicon.ico에는 맞지 않는다.
**경로 끝까지 0개 이상의 경로 칸. /css/**는 /css/bootstrap.min.css에도 /css/a/b.css에도 맞는다.

@Slf4jLombok. 클래스에 log 필드를 만든다. log.info("A [{}]", 값)은 {} 자리에 값을 넣어 앱 터미널에 출력한다 (Lombok: @Log).

MethodParameter파라미터 하나의 정보. hasParameterAnnotation(애너테이션.class)는 그 애너테이션이 붙었는지, getParameterType()은 선언한 타입을 돌려준다.
A.class.isAssignableFrom(B)B 타입의 값을 A 타입 변수에 넣을 수 있으면 true (Java 25: Class).
webRequest.getNativeRequest()NativeWebRequest가 감싼 원래 요청 객체. (HttpServletRequest)로 바꿔 세션을 꺼낸다 (교재 7장 721줄).

addArgumentResolvers로 등록한 리졸버는 스프링의 내장 파라미터 처리를 대체하지 않고 거기에 더해진다 (WebMvcConfigurer API). 표에 나온 어느 경우에도 맞지 않는 객체 타입 파라미터는 @ModelAttribute로 처리된다 (Spring: Method Arguments, 표 끝의 "Any other argument"). @ModelAttribute는 빈 객체를 새로 만들어 요청 파라미터를 바인딩한다(1회차).

    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
                         FilterChain chain)
            throws IOException, ServletException {
        // URI와 리다이렉트를 쓰려고 형변환
        HttpServletRequest req = (HttpServletRequest) request;
        HttpServletResponse res = (HttpServletResponse) response;
        if (!PatternMatchUtils.simpleMatch(allow, req.getRequestURI())) {
            res.sendRedirect("/notice");  // 응답을 정하고
            return;                       // 다음 단계로 넘기지 않는다
        }
        // 허용 경로만 다음 필터·서블릿으로
        chain.doFilter(request, response);
    }
}

@Configuration
public class MaintenanceConfig implements WebMvcConfigurer {

    @Bean                         // 돌려준 객체가 빈이 된다
    public FilterRegistrationBean<Filter> maintenanceFilter() {
        FilterRegistrationBean<Filter> bean = new FilterRegistrationBean<>();
        bean.setFilter(new MaintenanceFilter());          // 등록할 필터
        bean.setOrder(1);                                 // 낮을수록 먼저
        bean.addUrlPatterns("/*");                        // 모든 요청에 적용
        return bean;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new TimingInterceptor())
                .order(1)                                 // 인터셉터끼리의 순서
                .addPathPatterns("/api/**")               // /api 아래 전부
                .excludePathPatterns("/api/health");      // 이 경로는 뺀다
    }

    @Override
    public void addArgumentResolvers(
            List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new ClientIpArgumentResolver()); // 직접 만든 리졸버 등록
    }
}

// 인터셉터: 요청 처리 시간을 잰다
@Slf4j                                                    // log 필드가 생긴다
public class TimingInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        // 요청 하나에만 보관
        request.setAttribute("start", System.currentTimeMillis());
        return true;                                      // 계속 진행
    }

    // @Override: 시그니처가 틀리면 컴파일 오류로 알려 준다
    @Override
    public void postHandle(HttpServletRequest request,
                           HttpServletResponse response,
                           Object handler, ModelAndView modelAndView) {
        // 컨트롤러가 정상으로 끝났을 때만 불린다
        log.info("view={}", modelAndView);
    }

    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler, Exception ex) {
        // 예외가 나도 불린다
        long start = (long) request.getAttribute("start");
        long took = System.currentTimeMillis() - start;
        log.info("{} took {}ms", request.getRequestURI(), took);
    }
}

// 애너테이션: 파라미터에만, 실행 중에도 읽을 수 있게
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface ClientIp {
}

// 리졸버: @ClientIp String 파라미터에 접속 IP를 넣는다
public class ClientIpArgumentResolver implements HandlerMethodArgumentResolver {
    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        // @ClientIp가 있고 타입이 String이면 맡는다
        return parameter.hasParameterAnnotation(ClientIp.class)
                && String.class.isAssignableFrom(parameter.getParameterType());
    }

    @Override
    public Object resolveArgument(MethodParameter parameter,
                                  ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest,
                                  WebDataBinderFactory binderFactory) {
        HttpServletRequest request =
                (HttpServletRequest) webRequest.getNativeRequest();
        return request.getRemoteAddr();   // 이 값이 파라미터에 들어간다
    }
}

// 컨트롤러는 파라미터 하나로 받는다
@GetMapping("/api/me")
public String me(@ClientIp String ip) { return ip; }

A. 필터로 로그인 체크

클래스요구 사항
web.filter.LoginCheckFilterjakarta.servlet.Filter 구현. 화이트리스트 {"/", "/members/add", "/login", "/logout", "/css/*"}를 private static final String[]로 둔다. doFilter: 요청 URI가 화이트리스트에 맞지 않으면(PatternMatchUtils.simpleMatch) getSession(false)로 세션을 찾는다. 세션이 없거나 SessionConst.LOGIN_MEMBER 속성이 없으면 "/login?redirectURL=" + requestURI로 리다이렉트하고 return. 그 밖에는 chain.doFilter(request, response).
WebConfig(com.study.shop 바로 아래)@Configuration, implements WebMvcConfigurer. @Bean 메서드 loginCheckFilter(): FilterRegistrationBean<Filter>에 LoginCheckFilter, 순서 1, URL 패턴 "/*".
web.login.LoginController(수정)POST /login에 파라미터 @RequestParam(defaultValue = "/") String redirectURL을 더한다. 자리는 BindingResult 뒤 아무 곳이다. 성공하면 "redirect:" + redirectURL을 반환한다. 오류일 때의 처리는 그대로 둔다.

B. 인터셉터로 바꾸기

클래스요구 사항
web.interceptor.LogInterceptor@Slf4j, HandlerInterceptor 구현. 상수 public static final String LOG_ID = "logId";. preHandle: UUID를 만들어 request.setAttribute(LOG_ID, uuid), log.info("REQUEST [{}][{}][{}]", uuid, requestURI, handler), true 반환. postHandle: log.info("postHandle [{}]", modelAndView). afterCompletion: request.getAttribute(LOG_ID)로 UUID를 꺼내 log.info("RESPONSE [{}][{}]", logId, requestURI). ex가 null이 아니면 log.error("afterCompletion error!!", ex). 세 메서드 모두 @Override를 붙인다. 세 메서드가 default라서 이름이나 파라미터를 틀려도 컴파일은 되고 그 메서드만 안 불린다. 시그니처는 5절 예시의 TimingInterceptor와 같다.
web.interceptor.LoginCheckInterceptor@Slf4j, HandlerInterceptor 구현. preHandle만 구현한다. log.info("인증 체크 인터셉터 실행 {}", requestURI). 세션이 없거나 로그인 회원 속성이 없으면 log.info("미인증 사용자 요청"), "/login?redirectURL=" + requestURI로 리다이렉트, false 반환. 그 밖에는 true.
WebConfig(수정)addInterceptors 재정의. LogInterceptor: 순서 1, 적용 "/**", 제외 "/css/**", "/*.ico", "/error". LoginCheckInterceptor: 순서 2, 적용 "/**", 제외 "/", "/members/add", "/login", "/logout", "/css/**", "/*.ico", "/error". 그리고 loginCheckFilter()의 @Bean 한 줄을 주석 처리한다. 필터와 인터셉터가 같은 검사를 두 번 하지 않게 하기 위해서다 (교재 7장 630줄). LoginCheckFilter 클래스는 지우지 않는다.

C. @Login으로 로그인 회원 받기

클래스요구 사항
web.argumentresolver.Login애너테이션. @Target(ElementType.PARAMETER), @Retention(RetentionPolicy.RUNTIME). 본문은 비어 있다.
web.argumentresolver.LoginMemberArgumentResolverHandlerMethodArgumentResolver 구현. supportsParameter: @Login이 붙었고 타입이 Member이면 true. resolveArgument: getSession(false)로 세션을 찾아, 없으면 null, 있으면 SessionConst.LOGIN_MEMBER 속성을 반환.
WebConfig(수정)addArgumentResolvers 재정의. resolvers.add(new LoginMemberArgumentResolver()).
web.HomeController(수정)GET /의 파라미터 @SessionAttribute(name = SessionConst.LOGIN_MEMBER, required = false) Member member를 @Login Member member로 바꾼다. 분기는 그대로: null이면 뷰 home, 아니면 모델 member에 넣고 뷰 loginHome.

7. 실행하고 확인하기

먼저 확인할 것. 컨테이너 창에서 ./gradlew build가 통과했다. 8081을 쓰는 다른 컨테이너(옛 shop-docker-devcontainer)는 띄우지 않았다. 빌드가 실패하면 출력을 채팅에 붙여 넣는다.

앱은 컨테이너 창 터미널에서 ./gradlew bootRun으로 띄운다. 코드를 바꾼 뒤에는 Ctrl+C로 끄고 다시 띄운다. 앱을 다시 띄우면 세션은 모두 사라지고, TestDataInit이 상품 2개와 회원 test / test!를 다시 넣는다. curl은 컨테이너에 터미널을 하나 더 열어 친다.

2회차에 쓴 curl 옵션을 다시 적는다 (curl 매뉴얼). 새로 쓰는 것은 -o와 -w다.

옵션뜻
-s진행 표시를 숨긴다.
-i응답 본문 앞에 상태 줄과 응답 헤더도 출력한다.
-d '이름=값&…'그 값을 폼 데이터로 담아 POST로 보낸다.
-c 파일응답의 Set-Cookie로 받은 쿠키를 파일에 저장한다.
-b 파일 또는 -b '이름=값'파일에 저장한 쿠키나 적은 쿠키를 요청에 싣는다.
-o /dev/null응답 본문을 버린다(새로 씀).
-w '%{http_code}\n'요청이 끝난 뒤 상태 코드만 출력한다(새로 씀).
 
# 예시(과제와 다른 주소): 본문은 버리고 상태 코드만 본다
curl -s -o /dev/null -w '%{http_code}\n' http://example.com/

| grep -iE '패턴'은 출력에서 패턴이 든 줄만 남긴다(-i 대소문자 무시, -E |로 "또는"). 줄 끝의 \는 명령이 다음 줄로 이어진다는 표시다. 주소에 ?가 있으면 작은따옴표로 감싼다.

A 단계 확인(필터)

  1. 로그인 없이 상품 목록을 요청해 1절 흐름의 ①~④를 확인한다. 상태 코드, Location, Set-Cookie 유무를 본다.

    curl -s -i http://localhost:8081/items \
  | grep -iE '^HTTP|^location|^set-cookie'
  2. 로그인 없이 CSS 파일을 요청한다. 상태 코드는 200일까, 302일까?
    curl -s -o /dev/null -w '%{http_code}\n' \
  http://localhost:8081/css/bootstrap.min.css
  3. 아무 값의 JSESSIONID를 싣고 상품 목록을 요청한다. ① 상태 코드는? ② 응답에 Set-Cookie가 붙을까? 서버의 세션 저장소와 브라우저 쪽 쿠키를 나눠서 답한다.
    curl -s -i -b 'JSESSIONID=AAAA1111' http://localhost:8081/items \
  | grep -iE '^HTTP|^location|^set-cookie'
  4. redirectURL=/items를 붙여 로그인한다. 응답의 Location은 어디일까?
    curl -s -i -c /tmp/shop-cookie.txt \
  -d 'loginId=test&password=test!' \
  'http://localhost:8081/login?redirectURL=/items' \
  | grep -iE '^HTTP|^location|^set-cookie'

    받은 쿠키를 싣고 상품 목록을 연다. 상품 목록이 보이면 통과다.

    curl -s -b /tmp/shop-cookie.txt http://localhost:8081/items | grep '상품 목록'

    브라우저로도 한다. 통합 브라우저(명령 팔레트 "Browser: Open Integrated Browser")에서 로그아웃 상태로 http://localhost:8081/items를 연다. 주소창이 /login?redirectURL=/items가 되는지 보고, test / test!로 로그인한 뒤 상품 목록으로 돌아오는지 본다. 결과를 보기 전에 Ctrl+Shift+R로 캐시 없이 새로고침한다.

  5. (실험) LoginCheckFilter의 getSession(false)를 잠시 getSession()으로 바꾸고 앱을 다시 띄운다. 쿠키 없이 1번 명령을 다시 치면 ① Set-Cookie 줄이 생길까? ② 로그인하지 않은 방문자 1,000명이 상품 주소를 한 번씩 열면 서버 메모리에는 무엇이 쌓일까?

    확인이 끝나면 getSession(false)로 되돌리고 앱을 다시 띄운다.

B 단계 확인(인터셉터)

로그는 bootRun을 띄운 터미널에 나온다. 한 줄은 대략 … INFO … c.s.s.web.interceptor.LogInterceptor : REQUEST [uuid][/items][…] 모양이다. 줄 앞부분 형식은 환경마다 다를 수 있다.

  1. A 단계의 1번과 4번 명령을 다시 쳐서 결과가 필터 때와 같은지 본다.

  2. 로그아웃 상태에서 GET /items를 보낸다(A-1 명령). 앱 터미널에 REQUEST, 인증 체크 인터셉터 실행, 미인증 사용자 요청, postHandle, RESPONSE 가운데 어떤 줄이 어떤 순서로 찍힐까? 이어서 브라우저가 따라가는 /login 요청은 curl이 따라가지 않으니 여기서는 보지 않는다.

  3. B-1에서 앱을 다시 띄웠다면 세션이 사라졌으니 A-4의 로그인 명령부터 다시 친다.

    로그인한 쿠키로 GET /items를 보낸다(A-4의 두 번째 명령). 이번에는 어떤 줄이 어떤 순서로 찍힐까?

C 단계 확인(@Login)

  1. 로그인한 쿠키로 홈을 연다. 로그인: 테스터가 보이면 통과다. 쿠키 없이 열면 회원 가입이 보여야 한다.

    # 로그인한 쿠키를 싣고
curl -s -b /tmp/shop-cookie.txt http://localhost:8081/ \
  | grep -E '로그인:|회원 가입'
# 쿠키 없이
curl -s http://localhost:8081/ | grep -E '로그인:|회원 가입'

    앱을 다시 띄웠다면 세션이 사라졌으니 A-4의 로그인 명령부터 다시 친다.

  2. (실험) HomeController의 파라미터에서 @Login만 지우고(Member member만 남김) 앱을 다시 띄운다. 쿠키 없이 홈을 열면 어느 화면일까? 로그인: 뒤에는 무엇이 찍힐까?
    curl -s http://localhost:8081/ | grep -E '로그인:|회원 가입'

    확인이 끝나면 @Login을 되돌린다.

예측과 다르게 나온 것이 있으면 출력을 그대로 채팅에 붙여 넣는다. 끝나면 "다 했어"라고 알려 주면 채점한다.
