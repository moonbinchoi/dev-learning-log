2회차 · 회원 가입과 세션 로그인

스프링 MVC 2편 6장 리마인드 · Spring Boot 4.1.1 · 용어는 용어집

오늘의 결과물. shop에 홈 화면, 회원 가입, 로그인·로그아웃이 생긴다. 로그인하면 홈 화면에 "로그인: 테스터"가 뜨고, 로그아웃하면 다시 가입·로그인 버튼이 뜬다. 로그인 상태는 서버의 세션에 두고, 브라우저에는 세션 ID만 쿠키로 보낸다.

쿠키만으로 로그인을 유지하는 구현과 SessionManager 직접 구현은 하지 않는다. 면접에서는 "쿠키만 쓰면 왜 안 되는가"와 "세션은 언제 사라지는가"를 묻는다.

1. 동작 원리: 로그인 요청과 그다음 요청

로그인 한 번은 요청 두 건으로 끝난다. POST /login이 세션을 만들고 리다이렉트로 응답하면, 브라우저가 GET /을 보내면서 받은 세션 ID 쿠키를 함께 싣는다.

등장 객체역할
브라우저응답의 Set-Cookie로 받은 JSESSIONID를 쿠키 저장소에 보관하고, 같은 서버로 가는 요청마다 Cookie 헤더에 실어 보낸다.
LoginController분기한다. 검증 오류가 있거나 로그인 결과가 null이면 폼을 다시 그린다. 성공하면 세션을 만들어 회원을 넣고 /로 리다이렉트한다.
LoginService검사한다. 로그인 ID로 회원을 찾고 비밀번호를 비교해, 맞으면 그 회원을, 아니면 null을 돌려준다.
MemberRepository회원을 메모리 Map에 보관하고 로그인 ID로 찾아 준다.
세션 저장소(톰캣)세션 ID → 세션 객체(HttpSession)를 메모리에 둔다. ID는 추측할 수 없는 무작위 값으로 만들고, 정해진 시간 동안 요청이 없으면 그 세션을 지운다.
HomeController분기한다. 요청의 세션 ID로 찾은 세션에 loginMember가 있으면 loginHome, 없으면 home을 그린다.

  • 서버 처리
  • 응답·화면
  • 실패 분기
  • 서버에 남는 데이터
단계누가, 무엇을브라우저 쿠키세션 저장소
① 요청브라우저가 폼 값을 POST /login으로 보낸다.없음비어 있음
② 검증파라미터가 @Validated @ModelAttribute("loginForm") LoginForm form, BindingResult bindingResult 순서다. 스프링이 LoginForm에 바인딩한 뒤, @Validated가 붙어 있으니 @NotBlank를 검사해 오류를 바로 뒤의 BindingResult에 담는다. 오류가 있으면 컨트롤러가 hasErrors()로 보고 폼을 다시 그린다.없음비어 있음
③ 로그인 검사LoginService가 회원을 찾아 비밀번호를 비교한다. 결과가 null이면 컨트롤러가 reject()로 글로벌 오류를 넣고 폼을 다시 그린다.없음비어 있음
④ 세션 생성컨트롤러가 request.getSession()을 부른다. 세션이 없으니 톰캣이 새 세션을 만들고, 컨트롤러가 setAttribute("loginMember", 회원)으로 회원을 넣는다.없음ABC… → loginMember=회원 test
⑤ 응답컨트롤러가 redirect:/를 반환해 리다이렉트로 응답한다. 새 세션이 생겼으니 톰캣이 Set-Cookie: JSESSIONID=ABC…를 붙인다.JSESSIONID=ABC… 저장같음
⑥ 다음 요청브라우저가 Location의 /로 GET을 보내며 Cookie: JSESSIONID=ABC…를 싣는다.JSESSIONID=ABC…같음
⑦ 홈 분기톰캣이 쿠키의 ID로 세션을 찾고, @SessionAttribute가 그 안의 loginMember를 파라미터에 넣는다. HomeController가 값이 있으니 loginHome을 그린다. 세션이나 속성이 없으면 null이 들어오고 home을 그린다.JSESSIONID=ABC…같음

회원 정보는 서버를 떠나지 않는다. 브라우저가 가진 것은 추측할 수 없는 ID 하나뿐이고, 서버는 요청마다 그 ID로 자기 저장소를 찾는다 (교재 6장 859–874줄). 서블릿이 만드는 세션 쿠키 이름은 JSESSIONID이고 값은 추정할 수 없는 무작위 값이다 (교재 6장 1106–1108줄).

2. 쿠키만 쓰면 생기는 문제와 세션의 답

쿠키에 memberId=1처럼 회원 ID를 그대로 담아 로그인을 유지하면 문제가 셋 생긴다. 세션은 각 문제를 이렇게 막는다 (교재 6장 806–825줄, 878–882줄).

쿠키에 회원 ID를 담을 때세션을 쓸 때
값을 바꿀 수 있다. 브라우저에서 memberId=1을 2로 고치면 다른 회원이 된다.쿠키에는 추측할 수 없는 세션 ID만 있다. 아무 값이나 넣으면 서버 저장소에서 찾을 세션이 없다.
쿠키는 브라우저에 보관되고 요청마다 네트워크로 오가므로, PC나 전송 구간에서 정보를 훔칠 수 있다.세션 ID를 훔쳐도 그 안에 회원 정보는 없다.
한 번 훔친 쿠키를 계속 쓸 수 있다.서버가 세션 타임아웃을 짧게(예: 30분) 두고, 의심되면 그 세션을 서버에서 지운다.

세션도 쿠키를 쓴다. 교재는 이렇게 정리한다: "사실 세션이라는 것이 뭔가 특별한 것이 아니라 단지 쿠키를 사용하는데, 서버에서 데이터를 유지하는 방법일 뿐" (교재 6장 1092줄).

3. 핵심 요약

코드·설정동작
request.getSession()getSession(true)와 같다. 세션이 있으면 그것을, 없으면 새로 만들어 돌려준다 (교재 6장 1156–1170줄).
request.getSession(false)세션이 있으면 그것을, 없으면 null을 돌려준다. 새로 만들지 않는다. 공식 문서: "create가 false이고 요청에 유효한 세션이 없으면 null을 반환한다" (Servlet 6.1 API).
session.setAttribute(이름, 값)세션에 값을 넣는다. 한 세션에 여러 값을 넣을 수 있다 (교재 6장 1176줄).
session.invalidate()세션을 무효로 만들고 담긴 값을 모두 떼어 낸다 (HttpSession API). 로그아웃에 쓴다.
@SessionAttribute@SessionAttribute(name = "loginMember", required = false)로 쓴다. 이미 있는 세션에서 그 이름의 값을 꺼내 파라미터에 넣는다. 세션이나 값이 없으면 null이다. 세션을 만들지 않는다 (교재 6장 1232–1255줄, Spring: @SessionAttribute).
server.servlet.session.timeout모든 세션의 세션 타임아웃. 기본값은 30분이고, 단위를 안 붙이면 초다 (Boot: Application Properties, server.servlet.session.timeout 항목). 세션 하나만 바꾸려면 session.setMaxInactiveInterval(초)를 쓴다.
server.servlet.session.tracking-modes=cookie세션 ID를 쿠키로만 주고받는다. 이 설정이 없으면 첫 로그인 뒤 URL에 ;jsessionid=...가 붙을 수 있다. 서버가 첫 요청에서는 브라우저가 쿠키를 지원하는지 몰라 URL에도 ID를 싣기 때문이다 (교재 6장 1259–1273줄, 이유는 1265줄). 속성 자체는 Boot: Application Properties의 server.servlet.session.tracking-modes 항목에 있다.

홈 화면은 왜 세션을 만들지 않는가

홈 화면은 로그인하지 않은 사람도 연다. 여기서 getSession()을 부르면 방문자마다 쓸모없는 세션이 생겨 서버 메모리를 차지한다. 그래서 세션을 찾기만 하는 곳에서는 getSession(false)나 @SessionAttribute를 쓴다 (교재 6장 1221줄). 세션을 만드는 곳은 로그인 성공 처리 한 곳뿐이다.

세션은 언제 사라지는가

  • 로그아웃에서 invalidate()를 부를 때. 그런데 대부분의 사용자는 로그아웃하지 않고 브라우저를 닫는다. HTTP는 요청마다 연결이 끊기므로 서버는 사용자가 떠났는지 알 수 없다 (교재 6장 1352줄).
  • 그래서 타임아웃이 있다. 기준은 세션을 만든 시각이 아니라 마지막 요청 시각이다. 그 세션의 JSESSIONID를 실은 요청이 올 때마다 시계가 다시 시작되고, 마지막 요청 뒤 타임아웃 시간이 지나면 서버가 세션을 지운다 (교재 6장 1361–1363, 1383–1385줄). 공식 문서도 이 시간을 "클라이언트 요청 사이의 시간"으로 정의한다 (HttpSession API).
  • 세션을 끝없이 두면 훔친 JSESSIONID를 오래 쓸 수 있고, 세션이 메모리에 쌓인다. 메모리 사용량은 대략 세션에 넣은 데이터 크기 × 사용자 수다. 세션에는 꼭 필요한 데이터만 넣고, 시간은 기본 30분을 기준으로 정한다 (교재 6장 1356–1357, 1389줄).

4. Boot 4.1 차이

  • HttpServletRequest, HttpSession은 jakarta.servlet.http에서 import한다. Boot 4.1은 Jakarta EE 11(Servlet 6.1) 기반이다 (Boot: System Requirements). 교재 코드는 javax.servlet.http를 쓴다.
  • @PostConstruct는 jakarta.annotation.PostConstruct를 import한다. Spring Framework 7은 javax.annotation의 @PostConstruct 같은 애너테이션을 더 이상 지원하지 않는다 (Framework 7.0 Release Notes). 교재 6장 376줄은 javax.annotation.PostConstruct를 쓴다.
  • 교재는 타임아웃 글로벌 설정을 분 단위로 하라고 적었다 (교재 6장 1373줄). 이 레슨은 단위를 직접 붙여 1m처럼 쓴다. 단위를 붙이면 숫자의 뜻이 헷갈리지 않는다.

5. 오늘 쓰는 API

이름한 줄 설명
HttpServletRequest컨트롤러 파라미터로 받으면 지금 요청 객체가 들어온다. getSession()을 여기서 부른다.
HttpSession세션 하나. setAttribute, getAttribute, invalidate를 쓴다 (API).
@SessionAttribute세션 속성을 파라미터로 받는다. required = false면 없을 때 null. org.springframework.web.bind.annotation (문서). 클래스에 붙이는 @SessionAttributes(끝에 s)와 다르다.
bindingResult.reject(코드, 기본 문구)특정 필드가 아닌 객체 전체의 오류(글로벌 오류)를 넣는다. 템플릿은 ${#fields.globalErrors()}로 그린다 (교재 6장 508줄, Errors API).
Optional<T>값이 있을 수도 없을 수도 있음을 나타내는 상자. filter로 조건에 안 맞으면 비우고, orElse(null)로 비었을 때 null을 꺼낸다 (Java 25 API).
@PostConstruct빈 생성과 의존관계 주입이 끝난 뒤 그 메서드를 한 번 실행한다. 앱이 뜰 때 테스트 데이터를 넣는 데 쓴다 (교재 6장 365–401줄, Jakarta Annotations API).
@Service, @Component클래스를 스프링 빈으로 등록한다(컴포넌트 스캔). @Service는 서비스 계층용 이름이 붙은 @Component다. @Controller, @Repository도 같은 무리다 (Spring: Classpath Scanning).
@RequiredArgsConstructorLombok. final 필드를 받는 생성자를 만든다. 생성자가 하나뿐이면 스프링이 그 생성자로 빈을 주입한다(생성자 주입) (Lombok: Constructor).

예시: 과제와 다른 도메인(최근 본 책)

// 세션 속성 이름을 한곳에 둔다
public class RecentConst {
    public static final String RECENT_BOOK = "recentBookId";
}

@GetMapping("/books/{bookId}")
public String book(@PathVariable Long bookId,
                   HttpServletRequest request) {
    // 없으면 새로 만든다 = getSession(true)
    HttpSession session = request.getSession();
    // 이 브라우저의 세션에만 저장된다
    session.setAttribute(RecentConst.RECENT_BOOK, bookId);
    return "books/book";
}

@GetMapping("/recent")
public String recent(
        // 세션이나 값이 없으면 null. 세션을 만들지 않는다
        @SessionAttribute(name = RecentConst.RECENT_BOOK,
                          required = false) Long recentId,
        Model model) {
    if (recentId == null) {
        return "books/none";              // 본 책이 없다
    }
    model.addAttribute("recentId", recentId);
    return "books/recent";
}

@PostMapping("/recent/clear")
public String clear(HttpServletRequest request) {
    // 있으면 그 세션, 없으면 null
    HttpSession session = request.getSession(false);
    if (session != null) {
        session.invalidate();             // 세션과 값을 모두 버린다
    }
    return "redirect:/recent";
}

// 서비스에서 Optional을 null 규약으로 바꾸기
Book book = findByIsbn(isbn)
        .filter(b -> b.getStock() > 0)    // 재고가 없으면 비운다

domain.login.LoginService@Service, 저장소는 생성자 주입. Member login(String loginId, String password): 회원이 있고 비밀번호가 같으면 그 회원, 아니면 null.
web.member.MemberSaveForm@Data. loginId, password, name. 셋 다 @NotBlank(jakarta.validation.constraints).
web.login.LoginForm@Data. loginId, password. 둘 다 @NotBlank.
web.SessionConst상수 public static final String LOGIN_MEMBER = "loginMember"; 하나.
web.HomeController@Controller. 아래 표의 GET /.
web.member.MemberController@Controller, @RequestMapping("/members"). 아래 표의 두 메서드.
web.login.LoginController@Controller. 아래 표의 세 메서드.
TestDataInit(com.study.shop 바로 아래)@Component, 두 저장소를 생성자 주입. @PostConstruct 메서드에서 상품 2개(itemA·10000원·10개, itemB·20000원·20개)와 회원 1명(로그인 ID test, 비밀번호 test!, 이름 테스터)을 저장한다. 이제 앱을 다시 띄워도 이 데이터가 있다.
요청처리
GET /@SessionAttribute(name = SessionConst.LOGIN_MEMBER, required = false) Member로 받는다. null이면 뷰 home. 아니면 모델 member에 그 회원 → 뷰 loginHome. 세션을 만들지 않는다.
GET /members/add모델 member에 빈 MemberSaveForm → 뷰 members/addMemberForm
POST /members/add파라미터는 @Validated @ModelAttribute("member") MemberSaveForm form, BindingResult bindingResult 순서. 검증은 @Validated가 붙은 파라미터에만 돌고, BindingResult는 검증할 파라미터 바로 뒤에 둔다. 오류면 뷰 members/addMemberForm. 성공이면 Member를 만들어 저장하고 /로 리다이렉트.
GET /login모델 loginForm에 빈 LoginForm → 뷰 login/loginForm
POST /login파라미터는 @Validated @ModelAttribute("loginForm") LoginForm form, BindingResult bindingResult, HttpServletRequest request 순서. 오류면 뷰 login/loginForm. LoginService 결과가 null이면 reject("loginFail", "아이디 또는 비밀번호가 맞지 않습니다.") 후 같은 뷰. 성공이면 request.getSession()으로 세션을 얻어 SessionConst.LOGIN_MEMBER에 회원을 넣고 /로 리다이렉트.
POST /logoutrequest.getSession(false)로 세션을 찾아, 있으면 invalidate(). /로 리다이렉트.

비밀번호를 평문으로 저장·비교하는 것은 교재 예제 그대로다. 암호화는 Spring Security 범위라 이 과정에서 다루지 않는다.

설정

src/main/resources/application.properties에 한 줄을 더한다. 세션 ID를 쿠키로만 주고받게 한다.

server.servlet.session.tracking-modes=cookie

7. 실행하고 확인하기

먼저 확인할 것. shop 컨테이너 창에서 ./gradlew build가 통과했다. 8081을 쓰는 다른 컨테이너(옛 shop-docker-devcontainer)는 띄우지 않았다. 빌드가 실패하면 출력을 채팅에 붙여 넣는다.

컨테이너 창 터미널에서 앱을 띄운다. 코드나 설정을 바꾼 뒤에는 Ctrl+C로 끄고 다시 실행한다.

./gradlew bootRun

브라우저는 VS Code 명령 팔레트 "Browser: Open Integrated Browser"로 http://localhost:8081/을 연다. 결과를 보기 전에 Ctrl+Shift+R로 캐시 없이 새로고침한다. 회원 가입, test / test! 로그인, 틀린 비밀번호, 로그아웃을 화면에서 한 번씩 해 본다.

아래 단계는 컨테이너에 터미널을 하나 더 열고 curl로 한다. 쿠키를 직접 넣고 뺄 수 있기 때문이다. 쓰는 옵션 (curl 매뉴얼):

옵션뜻
-s진행 표시를 숨긴다.
-i응답 본문 앞에 상태 줄과 응답 헤더도 출력한다.
-d '이름=값&…'그 값을 폼 데이터로 담아 POST로 보낸다.
-c 파일응답의 Set-Cookie로 받은 쿠키를 파일에 저장한다.
-b 파일 또는 -b '이름=값'파일에 저장한 쿠키나 적은 쿠키를 요청에 싣는다.
 
# 예시(과제와 다른 주소): 검색어를 폼으로 POST하고, 받은 쿠키를 /tmp/a.txt에 저장
curl -s -i -c /tmp/a.txt -d 'q=spring' http://example.com/search
# 저장한 쿠키를 싣고 다음 페이지를 GET
curl -s -b /tmp/a.txt http://example.com/history
# 파일 대신 쿠키를 직접 적어 싣는다
curl -s -b 'lang=ko' http://example.com/

| grep -iE '패턴'은 출력에서 패턴이 든 줄만 남긴다(-i 대소문자 무시, -E |로 "또는"). 홈 화면 두 종류는 이렇게 구분한다: 로그인 후 홈에는 로그인: 테스터가, 로그인 전 홈에는 회원 가입이 있다.

  1. 쿠키 없이 홈 화면을 요청한다. 응답 헤더에 Set-Cookie 줄이 있을까, 없을까?
    curl -s -i http://localhost:8081/ | grep -iE '^HTTP|^set-cookie'
  2. curl로 로그인한다. ① 상태 코드는? ② Set-Cookie 줄이 있다면 쿠키 이름은?

    줄 끝의 \는 명령이 다음 줄로 이어진다는 표시다. 그대로 붙여 넣으면 된다.

    curl -s -i -c /tmp/shop-cookie.txt \
  -d 'loginId=test&password=test!' \
  http://localhost:8081/login \
  | grep -iE '^HTTP|^location|^set-cookie'

    방금 받은 쿠키를 싣고 홈을 연다. 화면이 어느 쪽인지 확인한다.

    curl -s -b /tmp/shop-cookie.txt http://localhost:8081/ \
  | grep -E '로그인:|회원 가입'
  3. 쿠키 값을 아무 값으로 바꿔 보낸다. 홈은 어느 화면일까? 응답에 Set-Cookie가 붙을까?
    curl -s -i -b 'JSESSIONID=AAAA1111' http://localhost:8081/ \
  | grep -iE '^set-cookie|로그인:|회원 가입'

    공식 문서는 "유효한 세션이 없으면 null"까지만 말한다. 모르는 ID가 "유효한 세션 없음"으로 처리되는지는 여기서 직접 확인한다.

  4. 2단계의 쿠키 파일을 싣고 로그아웃한 뒤, 같은 파일을 다시 싣고 홈을 열면 어느 화면일까?

    -d ''는 빈 폼 데이터를 POST로 보낸다. 로그아웃이 POST /logout이기 때문이다. 로그아웃에는 -c를 주지 않았으니 curl은 쿠키 파일을 고치지 않는다. cat으로 로그아웃 전후의 파일 내용이 같은지 본다.

    cat /tmp/shop-cookie.txt
curl -s -b /tmp/shop-cookie.txt -d '' http://localhost:8081/logout
cat /tmp/shop-cookie.txt
curl -s -b /tmp/shop-cookie.txt http://localhost:8081/ \
  | grep -E '로그인:|회원 가입'
  5. (실험) 타임아웃을 1분으로 줄인다. ① 브라우저에서 로그인한 뒤 1분 넘게 아무 요청도 하지 않고 새로고침하면 어느 화면일까? ② 로그인한 뒤 30초마다 새로고침하며 2분을 보내면 어느 화면일까?

    application.properties에 아래 줄을 더하고 앱을 다시 띄운다. 1m은 1분이다.

    server.servlet.session.timeout=1m

    확인이 끝나면 이 줄을 지우고 앱을 다시 띄운다. 기본값 30분으로 돌아간다.

예측과 다르게 나온 것이 있으면 출력을 그대로 채팅에 붙여 넣는다. 끝나면 "다 했어"라고 알려 주면 채점한다.
