1회차 · 상품 폼과 검증

스프링 MVC 2편 2~5장 리마인드 · Spring Boot 4.1.1 · 용어는 용어집, 한 장 요약은 폼·검증 요약

오늘의 결과물. shop에 상품 목록·상세·등록·수정 화면이 생긴다. 잘못 입력하면 입력값이 그대로 남은 채 빨간 오류 메시지가 뜨고, 저장한 뒤 새로고침해도 상품이 한 번만 저장된다.

진단에서 막힌 네 가지(PRG, th:field, BindingResult, 폼 객체 분리)만 다룬다. 면접에서는 각 항목의 "왜?"를 묻는다.

1. PRG: 저장 후에는 리다이렉트한다

문제. POST로 저장한 뒤 컨트롤러가 상세 뷰를 바로 반환하면, 브라우저의 마지막 요청은 그 POST로 남는다. 이 화면에서 새로고침(F5)을 하면 브라우저는 마지막 요청인 POST를 폼 데이터와 함께 다시 전송하고, 상품이 또 저장된다 (Wikipedia: Post/Redirect/Get).

해결. POST를 처리한 뒤 뷰를 그리지 않고 리다이렉트로 응답한다. 브라우저는 상세 페이지를 GET으로 새로 요청하고, 이제 마지막 요청은 GET이다. 새로고침하면 그 GET만 다시 보낸다. 이것이 PRG(Post/Redirect/Get)다.

메시지 전달. 리다이렉트하면 모델이 사라지므로 "저장되었습니다"를 URL에 실어 보낸다. RedirectAttributes의 addAttribute로 넣은 값은 리다이렉트 URL의 {이름} 자리를 채우고, 남은 값은 쿼리 파라미터로 붙는다 (교재 4장 129–133줄의 코드). 공식 문서는 "모델 속성은 리다이렉트 URL의 URI 템플릿 변수로 쓰이고, 남은 기본 타입 속성은 쿼리 파라미터로 붙는다"고 설명한다 (Spring: Redirect Attributes).

redirectAttributes.addAttribute("itemId", 1L);    // {itemId} 자리에 1
redirectAttributes.addAttribute("status", true);  // 자리가 없으니 ?status=true
return "redirect:/items/{itemId}";               // → /items/1?status=true

상세 템플릿은 <h2 th:if="${param.status}" th:text="'저장 완료'"></h2>로 쿼리 파라미터를 읽는다 (교재 3장 534줄).

현재 요청 URL의 경로 변수는 따로 넣지 않아도 리다이렉트 URL에 쓸 수 있다. 그래서 수정 처리(POST /items/{itemId}/edit)는 return "redirect:/items/{itemId}";만 써도 된다 (같은 공식 문서).

2. th:field가 만드는 것

th:object="${item}"로 폼의 커맨드 객체를 고르면, 폼 안에서 선택 변수 식 *{필드}로 그 객체의 필드를 가리킨다. th:field는 그 필드 이름과 값으로 HTML 속성 세 개를 만든다 (교재 2장 84–142줄, Thymeleaf + Spring 6.2 Inputs).

<!-- 템플릿 -->
<input type="text" th:field="*{itemName}">
<!-- 렌더링 결과: 이름이 같은 id·name, 그리고 현재 값 -->
<input type="text" id="itemName" name="itemName" value="상품A">
  • name: 제출할 때 요청 파라미터 이름이 된다. 그래서 @ModelAttribute가 같은 이름의 필드에 값을 넣는다.
  • value: 등록 폼(빈 객체)이면 value="". 검증에 실패해 폼을 다시 그리면 사용자가 입력했던 값이 들어간다(3절의 rejectedValue).

오류 표시용 속성 두 개 (교재 4장 509–511줄. th:errorclass는 Thymeleaf + Spring 7.1 Field errors에도 있다):

속성동작
th:errors="*{price}"price에 오류가 있을 때만 태그를 그리고, 오류 메시지를 넣는다.
th:errorclass="field-error"같은 태그의 th:field 필드에 오류가 있을 때만 class에 field-error를 덧붙인다.

3. BindingResult: 오류가 나도 컨트롤러까지 온다

BindingResult는 바인딩·검증 오류를 담는 객체다. 검증할 @ModelAttribute 파라미터 바로 다음에 둔다. 그 위치로 어떤 객체의 오류인지 안다 (교재 4장 555줄).

가격 칸에 abc를 제출했을 때결과
BindingResult 있음컨트롤러가 정상 호출된다. 스프링이 price에 typeMismatch FieldError를 만들어 담는다. 이 FieldError는 입력값 abc(rejectedValue)도 보관한다 (교재 4장 536–545, 661줄).
BindingResult 없음컨트롤러가 호출되지 않고 400 오류 페이지가 뜬다 (교재 4장 540줄). 공식 문서: BindingResult가 없으면 예외가 발생한다 (Spring: @ModelAttribute).

검증 순서. ① 각 필드의 타입 변환 → 실패한 필드는 typeMismatch 추가. ② 변환에 성공한 필드에만 Bean Validation 적용. 변환에 실패한 필드에 @NotNull 같은 검사는 돌지 않는다 (교재 5장 385–408줄). 공식 문서에서는 이 순서를 찾지 못했으니 8절 2단계에서 직접 확인한다.

BindingResult는 모델에도 자동으로 담긴다(교재 4장 556줄). 그래서 오류가 있을 때 리다이렉트하지 않고 폼 뷰 이름을 그대로 반환하면, 템플릿이 입력값과 오류를 함께 그린다.

4. 등록·수정 폼 객체를 나누는 이유

교재(5장 825–891줄)의 이유는 "문법이 간단해서"가 아니다. 받는 데이터와 검증 규칙이 다르기 때문이다.

  • 실무 폼은 도메인 객체와 딱 맞지 않는다. 약관 동의처럼 Item에 없는 데이터가 넘어오고, 등록과 수정은 받는 범위도 다르다(예: 회원 가입에만 로그인 ID).
  • Item 하나로 받으면 등록·수정 규칙을 한 클래스에 섞어야 하고, 이를 구분하려면 groups가 필요하다. groups를 쓰면 Item과 코드 전반의 복잡도가 올라간다.
  • ItemSaveForm·ItemUpdateForm으로 나누면 각자 자기 규칙만 가진다. 등록·수정이 완전히 분리되니 groups를 쓸 일이 드물다.
  • 대가: 컨트롤러에서 폼 객체 → Item으로 옮기는 코드가 생긴다.

흐름: HTML 폼 → ItemSaveForm → 컨트롤러 → Item 생성 → 저장소

5. Boot 4.1 차이

  • javax.* 대신 jakarta.*. @NotBlank·@NotNull·@Max는 jakarta.validation.constraints에서 import한다.
  • Hibernate Validator 9에서 org.hibernate.validator.constraints의 @NotBlank·@NotEmpty·@Email은 삭제됐다. 삭제 목록은 HV Migration Guide에 있다. @Range는 HV 9.1 API 문서에 deprecated 표시 없이 그대로 있다 (Range API).

6. 오늘 쓰는 API

이름한 줄 설명
@Validated이 파라미터를 바인딩한 뒤 Bean Validation을 실행한다. org.springframework.validation.annotation (API).
@ModelAttribute("item")요청 파라미터를 객체에 바인딩하고, 모델에 item이라는 이름으로 담는다. 이름을 빼면 ItemSaveForm은 itemSaveForm으로 담겨 템플릿의 ${item}과 어긋난다 (교재 5장 1108줄).
BindingResulthasErrors()로 오류가 있는지 확인한다.
RedirectAttributesaddAttribute(이름, 값)으로 리다이렉트 URL에 값을 싣는다.
@NotBlank문자열이 null·빈 문자열·공백만이면 오류. 아래 제약 애너테이션 넷의 공식 설명은 HV 9.1 레퍼런스 2.3 Built-in constraints.
@NotNullnull이면 오류. 숫자 칸을 비워 제출하면 null이 된다.
@Range(min, max)숫자가 min~max(양 끝 포함) 밖이면 오류.
@Max(value)숫자가 값보다 크면 오류.

예시: 과제와 다른 도메인(회원 가입)

@Data                                   // Lombok: getter·setter·기본 생성자 등
public class MemberJoinForm {
    @NotBlank                           // jakarta.validation.constraints.NotBlank
    private String loginId;
    @NotNull @Range(min = 14, max = 120) // 비우면 @NotNull, 범위 밖이면 @Range 오류
    private Integer age;
}

@PostMapping("/members/join")
public String join(@Validated @ModelAttribute("member") MemberJoinForm form, // 바인딩 + 검증, 모델 키 "member"
                   BindingResult bindingResult,                            // 바로 앞 파라미터의 오류
                   RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
        return "members/joinForm";       // 리다이렉트 없이 폼을 다시 그린다(입력값·오류 유지)
    }
    Member saved = memberRepository.save(new Member(form.getLoginId(), form.getAge())); // 폼 → 도메인
    redirectAttributes.addAttribute("memberId", saved.getId()); // {memberId} 자리
    redirectAttributes.addAttribute("joined", true);            // ?joined=true
    return "redirect:/members/{memberId}";                      // PRG
}

7. 과제: shop에 상품 관리 만들기

Java 코드는 직접 쓴다. 템플릿·CSS·메시지 파일은 교재 예제에서 복사한다. 베이스 패키지는 com.study.shop이다. 원본 경로는 저장소 루트(E:\Study\Inflearn) 기준, shop의 위치는 projects/shop 기준이다.

복사할 파일

원본shop의 위치
templates/validation/v4/의 html 4개src/main/resources/templates/items/
static/css/bootstrap.min.csssrc/main/resources/static/css/
messages.propertiessrc/main/resources/

복사는 호스트 창(루트 E:\Study\Inflearn)의 탐색기에서 한다. 컨테이너 창에는 courses/가 보이지 않는다.

그다음 컨테이너 창에서 Ctrl+Shift+H(전체 찾기·바꾸기)를 열고, "포함할 파일"에 src/main/resources/templates/items를 넣은 뒤 /validation/v4/items를 모두 /items로 바꾼다. 호스트 창에서 하면 교재 예제 코드까지 바뀐다.

템플릿의 #{page.items} 같은 표현은 messages.properties에서 같은 키의 문구를 읽는다. 스프링 부트는 기본으로 messages.properties를 메시지 파일로 쓴다 (Boot: Internationalization).

# 한 줄에 키=문구 하나
page.items=상품 목록
button.save=저장
# 템플릿의 #{page.items} 자리에 "상품 목록"이 들어간다

만들 클래스

클래스요구 사항
domain.item.Item@Data. 필드 Long id, String itemName, Integer price, Integer quantity.
domain.item.ItemRepository@Repository. 메모리 저장(Map<Long, Item>와 증가하는 long 순번). 메서드 Item save(Item)(id를 부여하고 그 Item을 반환), Item findById(Long)(없으면 null),findAll()(List<Item>), update(Long itemId, Item updateParam)(이름·가격·수량을 덮어씀).
web.item.form.ItemSaveForm@Data. itemName: @NotBlank. price: @NotNull, @Range(min = 1000, max = 1000000). quantity: @NotNull, @Max(9999). id 필드는 없다.
web.item.form.ItemUpdateForm@Data. id: @NotNull. itemName: @NotBlank. price: @NotNull, @Range(min = 1000, max = 1000000). quantity: 제약 없음(수정 때는 자유).

요청처리
GET /items모델 items에 전체 목록 → 뷰 items/items
GET /items/{itemId}모델 item에 상품 → 뷰 items/item
GET /items/add모델 item에 new Item() → 뷰 items/addForm
POST /items/addItemSaveForm을 검증. 오류면 뷰 items/addForm. 성공이면 Item을 만들어 저장하고 /items/{itemId}?status=true로 리다이렉트.
GET /items/{itemId}/edit모델 item에 상품 → 뷰 items/editForm
POST /items/{itemId}/editItemUpdateForm을 검증. 오류면 뷰 items/editForm. 성공이면 이름·가격·수량을 수정하고 /items/{itemId}로 리다이렉트.

템플릿은 폼 객체를 ${item}으로 읽는다. 두 POST 메서드의 폼 파라미터에 모델 이름 item을 지정한다.

8. 실행하고 확인하기

먼저 확인할 것. shop 컨테이너 창이 열려 있고, 그 창에서 ./gradlew build가 통과했다. 8081을 쓰는 다른 컨테이너(옛 shop-docker-devcontainer)는 띄우지 않았다. 빌드가 실패하면 출력을 채팅에 붙여 넣는다.

컨테이너 창 터미널에서 실행한다. bootRun은 앱을 띄우는 Gradle 작업이다. 포트는 dev container 설정으로 8081이다.

./gradlew bootRun

브라우저는 VS Code 명령 팔레트 "Browser: Open Integrated Browser"로 http://localhost:8081/items를 연다. 결과를 보기 전에 Ctrl+Shift+R로 캐시 없이 새로고침한다.

  1. 컨테이너에 터미널을 하나 더 열고 아래 명령을 치기 전에 적어 보자: 등록 폼의 상품명 <input>에는 어떤 속성들이 어떤 값으로 찍혀 나올까?

    curl -s URL은 그 주소의 HTML을 그대로 출력한다(-s는 진행 표시를 숨긴다). | grep 단어는 그중 그 단어가 든 줄만 남긴다.

    curl -s http://localhost:8081/items/add | grep itemName
  2. 등록 폼에서 상품명은 비우고, 가격에 abc, 수량에 99999를 넣고 저장하면? ① 화면은 어느 페이지인가 ② 가격 칸에는 무엇이 남아 있나 ③ 가격 칸 아래 오류 메시지는 몇 개인가

    문구 내용은 신경 쓰지 않는다. 오류 문구 파일(errors.properties)을 복사하지 않았으니 스프링 기본 문구가 나오고, 가격 문구는 길고 어색하다.

  3. 이번엔 올바르게 입력해 저장한다. ① 주소창의 URL은? ② 그 화면에서 F5를 누른 뒤 목록에 가 보면 상품은 몇 개인가

  4. 수정 화면에서 가격을 500으로 바꿔 저장해 오류가 뜨는지, 수량을 비워도 저장되는지 확인한다.

  5. (실험) POST /items/add 메서드에서 BindingResult 파라미터와 그것을 쓰는 코드를 잠깐 지우고, 가격에 abc를 넣어 저장하면 화면은?

    코드를 바꾼 뒤에는 실행 중인 앱을 Ctrl+C로 끄고 ./gradlew bootRun을 다시 실행한다. 확인한 뒤 원래대로 되돌린다. 여유가 있으면 BindingResult를 폼 파라미터 앞으로 옮겨도 보자. 이 경우는 교재에 결과가 없으니 직접 본 것을 알려 주면 된다.

예측과 다르게 나온 것이 있으면 그대로 채팅에 붙여 넣는다. 끝나면 "다 했어"라고 알려 주면 채점한다.
